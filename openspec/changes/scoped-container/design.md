## Context

动机见 `proposal.md`。以下是塑造方案的关键事实，三处 `@cage` 硬伤均已在当前代码基上实测复现。

**三处实测行为**

| 项 | 实测输出 |
|---|---|
| 注册表键 | `['Service']` —— 只有类名。两个同名类：`b.who()` 返回**第一个** Service，`a is b == True` |
| 装饰后类型 | `type(Service).__name__ == 'function'`；`issubclass(Service, object)` → `TypeError`；`isinstance(a, Service)` → `TypeError` |
| 生命周期入口 | `cage` 模块公开名为空；`reset`/`destroy`/`scope`/`clear` 均无 |

**根因（决定了方案的方向）**：装饰器只能返回别的东西，所以"用装饰器实现单例"必然走"替换类"这条路，而替换类必然摧毁类型契约。DI 的正确性要求——键唯一、类型可判定、作用域、生命周期、可替换——**在装饰器语义里无处安放**。因此方案不是"修好 `@cage`"，而是给 DI 一个**有身份的容器**。

**需求侧的修正**：原表述"跨 Worker 拿到**同一个**对象"里的"全局同一性"是错目标——进程级全局单例会让两个用户的 agent 共享工具客户端（串会话数据），或让两台设备共享连接句柄（写错设备）。真正需要的是**作用域解析**。

**覆盖现状**：`@cage` 此前**没有任何 spec 覆盖**；已在 **8 处**使用，**全部是进程级管理器**——对它们而言全局同一性是对的。所以本变更不废除全局共享，而是把**作用域显式化**。

**8 处使用点的实测清点**（tasks 1.3；"线程安全归属"一列是对**当前代码**的判定，不是对改造后行为的期望）

| # | 使用点 | 作用域 | 持有的可变状态 | 线程安全归属（实测） |
|---|---|---|---|---|
| 1 | `event/event_channel_manager.py` · `EventChannelManager` | 进程级 | 无实例字段；类级持有 `EventChannelRegister` 单例 | **无状态**（全 classmethod，纯转发） |
| 2 | `event/event_channel_register.py` · `EventChannelRegister` | 进程级 | 类级 `_channel_map: ThreadSafeDict` | **依赖内部锁**；但 check-then-act 不原子 → **F2** |
| 3 | `event/event_provider.py` · `EventProvider` | 进程级 | 类级引用 `_eventChannelRegister`（写一次，之后只读） | **无状态**（纯转发） |
| 4 | `event/event_register.py` · `EventRegister` | 进程级 | `self.event_list = []` —— **裸 list** | **无任何保证** → **F1** |
| 5 | `reactor/event_reactor_manager.py` · `EventReactorManager` | 进程级 | `reactor_map: ThreadSafeDict` + `_registry_lock: RLock` | **依赖内部锁**（8 处中唯一显式加锁者） |
| 6 | `reactor/waiter_result_reactor.py` · `WaiterResultReactor` | 进程级 | 继承 `EventReactor` 的 `retry_strategy`/`retry_times`/`handle_callback`/`error_callback`，加自身 `worker_names`/`on_result`/`_event_timeout` | **实例自身不保证** → **F4** |
| 7 | `statemachine/state_machine_manager.py` · `StateMachineManager` | 进程级 | `_state_scope_map: ThreadSafeDict` + `_local_store_loaded: bool`（裸 bool） | **依赖内部锁**；但复合操作不原子 → **F3** |
| 8 | `statemachine/state_node_index_factory.py` · `StateNodeIndexFactory` | 进程级 | **无** | **无状态**（单个 classmethod） |

结论：作用域 **8/8 为进程级**，与"全局同一性对它们而言是对的"相符，迁移即注册为进程级作用域。线程安全归属的实际分布是 **无状态 3 / 依赖内部锁 3 / 无任何保证 2**——**不是**清一色的"依赖内部锁或无状态"。后 2 处（表中加粗的两行）使 D5 从"把沉默变成明示"变成"必须先把沉默处的缺陷认下来"，见下。

**清点中发现的四处既有缺陷**（均不加锁；1 与 4 处在此变更的"声明必填"落地前只会被沉默地共享）

- **F1 · `EventRegister.event_list` 是进程级单例上的裸 list**（无锁）。`register`/`unregister` 就是 `list.append`/`list.remove`，并发下会损坏或以 `ValueError` 失败。该模块目前只被 `event/__init__.py` 再导出、**框架内部无调用点**，故为**潜在**缺陷——但它是公开导出面，任何导入方拿到的都是同一个无保护 list。
- **F2 · `EventChannelRegister.get_channel` 的 check-then-act 不原子**：map 本身线程安全，但"查不到就建、再写入"是两步。两个线程可同时判断为缺、各建一个 `EventChannel`，其中一个连同其已注册的 reactor 被静默丢弃。
- **F3 · `StateMachineManager` 的复合操作不原子**：`get_and_create_scope`/`create_scope`/`set_state` 都是"`get` 判空 → `create` → 再取"，并发首次写入可产生两个 `StateScope` 并丢掉其中一份状态；`_local_store_loaded` 是裸 bool，也无保护。**注意这条正落在 `scheduler-model-seam` 第 4.5 组的归属写入路径上**——该组的用例是单线程的，故未能暴露。
- **F4 · `WaiterResultReactor`（及基类 `EventReactor`）在执行期读共享可变字段**：`_execute` 会读 `self.retry_strategy`/`self.retry_times`，而 `worker_names`/`on_result` 由调用方在派发之外赋值（测试即如此用），两者之间没有栅栏。当前之所以没出事，是因为赋值都发生在启动/绑定期的单线程阶段——这是**时序上的侥幸，不是保证**。

F1–F4 都**不在本变更的修复范围内**（本变更是把归属显式化并让声明必填，不是修这些 manager 的并发）。处置方式是：在迁移这 8 处时，把 F1/F4 如实声明为"仅限单线程/不保证"，把 F2/F3 记为独立缺陷并在 spec 中不声称已修。

**硬前置**：本变更依赖 `scheduler-model-seam` 引入的**会话标识**来充当会话作用域的边界。该标识未落地前，作用域只能退化为进程级，等于没做——故 tasks 第 1 组即为该前置的核对。

## Goals / Non-Goals

**Goals**

- 让"跨 Worker 复用同一个对象"以**可声明作用域**的方式成立，而不是全局单例
- 消灭实测的三处硬伤：同名串号、类型契约被摧毁、无生命周期
- 为测试提供可替换实现的接缝
- 把线程安全归属从"沉默"变为"注册必填"
- 把框架自身的 8 处进程级共享从隐式全局状态改为显式注册

**Non-Goals**

- **不做 AOP**：不施加通知、不定义连接点、不做切点匹配
- 不做构造期自动装配图、循环依赖检测、配置驱动 bean 定义
- 不重构 `aop/` 包内与 DI 无关的装饰器（`params`/`configure`/`logger`/`stopwatch`/`validation`）
- 不改 `@params` 的配置机制
- 不引入 Rust，不改依赖列表

## Decisions

### D1 · 载体：显式容器 + 作用域句柄；装饰器若保留则只登记、不替换类

- **选**：容器是一个显式对象，注册与解析都是方法调用；作用域以显式句柄表达（进程级句柄 / 会话级句柄）。装饰器**可以**保留为语法糖，但 MUST 只在类定义处完成登记，**MUST NOT 替换类本身**。
- **理由**：三处硬伤全部源自"装饰器只能返回别的东西"。类型契约那一条已实测导致 `issubclass`/`isinstance` 双废，并已造成过一次 P0。DI 的其余要求（键、作用域、生命周期、可替换）也都需要容器有身份才能承载。
- **已考虑的替代**：① 装饰器返回代理对象以保留类型契约——拒绝，代理仍无法提供作用域与生命周期，且会改变 `__init__` 语义；② 用 `contextvars` 承载作用域——拒绝，见 D3。

### D2 · 注册项标识取「模块 + 限定名」，允许显式名覆盖

- **选**：默认标识为 `f"{cls.__module__}.{cls.__qualname__}"`；允许以显式名覆盖。
- **理由**：实测同键只取 `cls.__name__`，导致同名类解析到**错的对象且不报错**。限定名在进程内唯一；显式名用于兼容既有命名与提供稳定句柄。
- **已考虑的替代**：仅用显式名——拒绝，注册负担过重且容易漏，漏了就退化成匿名项。

### D3 · 作用域传递走显式句柄，不从上下文变量隐式取

- **选**：作用域句柄显式传入（或由已持有它的对象注入）。上下文变量只作**便利读法**，且跨线程派发时必须显式复制上下文。
- **理由**：与 `scheduler-model-seam` 的 **D3 必须保持一致**——`ThreadPoolExecutor` 提交的任务不继承调用方的上下文变量。隐式取作用域一旦落空，后果比"丢标识"更严重：会**取到别的会话的对象**（串作用域），而这是静默的。
- **交叉引用**：本决策是该变更 D3 的直接推论，两处都写明"显式句柄为真相来源"，避免两个变更互相矛盾。

### D4 · 生命周期用「显式获取 + 显式释放」，释放触发销毁钩子；不做引用计数

- **选**：作用域级 `release`/`close`；作用域结束即释放；注册项 MAY 声明 `on_release` 钩子；释放幂等（重复释放不报错、钩子不重复调用）。
- **理由**：引用计数在跨 Worker 时无法可靠——谁持有谁释放不确定，异常路径会泄漏计数。而"每会话一个 / 每设备一个"的匹配对象是**作用域归属**，不是引用数。幂等是必须的：作用域释放会与异常路径重叠。
- **已考虑的替代**：`__del__` 或 `weakref.finalize`——拒绝，二者在解释器退出与循环引用下不可靠，而设备/Agent 场景恰恰要求"连接一定被关掉"。

### D5 · 线程安全归属作为注册的必填声明

- **选**：注册时必须三选一：容器保证串行 / 实例自身保证 / 仅限单线程作用域。未声明则**拒绝注册**。
- **理由**：跨 Worker 共享可变对象是并发的脚枪，而 `@cage` 现状对此**完全沉默**，它共享的却正是有状态的 manager。隐式默认一个安全假设，正是这类缺陷的温床。
- **已考虑的替代**：默认"实例自身保证"——拒绝，理由同上。
- **声明的落地方式（实现时收紧，均在 spec 允许范围内）**：声明不是装饰性的注解，每一条都要有对应的行为，否则"写了等于没写"：
  - 「容器保证串行」→ 该注册项**不得直接 `resolve()`**，须经 `exclusive()` 取用（块内互斥，返回**真实实例而非代理**，故 D1/D2 的类型契约不受影响；锁可重入，实例方法内再次进入不自锁）。若允许 `resolve()` 直接取走实例，这条保证就是空的。
  - 「仅限单线程」→ 绑定到**首次取用它的线程**，此后不符线程的取用**明确拒绝**。spec 写的是"被拒绝或显式告警"，此处取更严的**拒绝**：既然声明了这条约束，越界使用就该当场失败；真需要跨线程的项属于另两种声明，应当去改声明而不是放宽检查。
  - 「实例自身保证」→ 容器不做任何额外动作（这是唯一"什么都不用做"的声明，也是最需要如实填写的——把无锁的可变对象填成它，等于把一个未验证的安全假设写进代码）。

### D6 · 首期只做「解析 + 生命周期」，不做自动装配

- **选**：一期范围为注册 → 按作用域解析 → 释放，外加测试替换与重置。不做构造期依赖图、不做循环依赖检测、不做配置驱动 bean。
- **理由**：先把**正确性**（键唯一、类型契约、作用域、生命周期、线程安全声明）做对。自动装配是便利层，早做会把尚未验证的正确性假设固化进装配图——那正是 `@cage` 当初的路径。
- **已考虑的替代**：一步做到 Spring 风格自动装配——拒绝，范围过大且会掩盖 D1–D5 的问题。

### D7 · `aop/` 包：不搬家、不重构，但划清边界并禁止蔓延

- **选**：本变更**不**重构 `aop/` 内其他装饰器；只做两件事：把 8 处 `@cage` 使用点改为显式进程级注册；留下约束使"用装饰器替换类"不再新增。
- **理由**：一次改完会让范围失控（`params` 的 import 期冻结、`logger` 的装饰期挂 handler、`stopwatch` 用墙钟，各自都是独立问题）。但**必须留下"不许扩大"的约束**——否则同一模式会继续蔓延，而它每次蔓延都可能再制造一个 P0。
- **附带记录**：`@cage` 无 spec 覆盖这一事实本身值得写下——它意味着这个被 8 处依赖的机制此前从未被规格化。

### D8 · 同一反模式的第二处：`@params` 的缓存键一并改为限定名

`core/aop/params.py` 用 `config_params[cls.__name__]` 缓存已解析的参数类——**与 D2 所修的 `@cage` 是同一个反模式**。后果更隐蔽：同名参数类会跳过解析并**直接复用他人的配置值**，发生在 import 期且无任何提示。

- **选**：缓存键由裸类名改为限定名（模块 + 限定名），与 D2 取同一策略。
- **理由**：同一根因应用同一修法；分开做要重复一次测试与验证，而收益相同。且 `@params` 的别名回退与假值语义是刚获得、尚无 spec 覆盖的行为，借这次一并固定以防回归。
- **已考虑的替代**：① 立独立小变更专修此键——拒绝，根因与修法相同，拆开只是重复验证；② 只记录不修——拒绝，它是静默取错值，与 `@cage` 的串号属同一严重度。
- **执行顺序上的例外**：本决策的实现在任务中单列一组，**不受 1.1 的硬前置约束**——它不依赖会话标识，可与容器部分并行推进。把 1 行的键修正压在一个 26 任务重构之后才做，是错误的排期。
- **实测中发现的额外坑（供后续碰 `aop/` 的实现者注意）**：`import zoo_framework.core.aop.params as m` 绑定的是**函数**而非子模块（包 `__init__` 的 `from .params import params` 覆盖了子模块属性），而对函数对象 `setattr` 会**静默成功**。测试里若用这种写法去"清缓存"，实际是给函数加了个属性、缓存从未清空——会让用例因串扰而失败或**因串扰而误过**。取子模块必须用 `importlib.import_module("zoo_framework.core.aop.params")`。

## Risks / Trade-offs

**[与 `scheduler-model-seam` D3 冲突的风险] → ** 两处都涉及"作用域/标识如何跨线程传递"，若各写一套会互相矛盾。缓解：本变更 D3 直接引用并服从该决策，两处都写明"显式句柄为真相来源"，且在 tasks 中把"前置核对"放在第 1 组。

**[迁移 8 处 `@cage` 使用点可能改变解析时机与身份] → ** 这些点都是进程级 manager，注册为进程级作用域即可保持行为。缓解：以既有 `test_event.py`、`test_reactor.py`、`test_zoo_framework.py`、`test_state_machine.py` 作回归；迁移按点逐个提交，任一点转红即回退该点。

**[`tests/test_aop.py` 现有两条断言会被推翻] → ** `test_cage_decorator` 断言"装饰后能被正常实例化"，`test_cage_singleton_behavior` 断言 `instance1 is instance2`。若 `@cage` 的语义变更（标识改限定名、不再替换类），这两条必须改写。这是**对既有已测试契约的修改**，在此明示；改写时保持断言语义（"能实例化""单例语义成立"）不变，只改调用与断言主体。

**[线程安全必填声明会拒绝现有注册] → ** 初次落地时所有注册都会被拒，直到补声明。缓解：首期只对**经容器注册**的项要求该声明；`@cage` 的既有 8 处按**实测归属**如实声明——6 处写"实例自身保证"（3 处无状态、3 处依赖内部锁），2 处（`EventRegister`、`WaiterResultReactor`，见清点表 F1/F4）**不得**写"实例自身保证"，只能写"仅限单线程"或以容器串行兜住。**这正是把沉默变成明示的意义**：若照搬"它们本就安全"的假设，就会把一个未验证的安全断言写进声明，比不写更糟。F2/F3 是既有缺陷，本变更不修，也不声称已修。

**[作用域句柄的显式传递会增加调用点噪音] → ** 每个取用共享对象的地方都要能拿到作用域句柄。缓解：句柄随运行/会话上下文传播（由 `scheduler-model-seam` 的标识机制承载），Worker 侧通过运行期对象读取即可，不需要逐层手工传参。

**[不做自动装配会让使用侧仍要手写解析] → ** 便利性提升有限，可能被认为"不如 `@cage` 好用"。缓解：这是刻意的取舍——先正确后便利；且 D1 允许装饰器作为语法糖存在，只是不得替换类，所以"声明式"的书写体验可以保留。

## Open Questions

- 容器与作用域的命名（`ScopedContainer` / `Scope` / `resolve` 等）与模块位置（放在 `core/` 还是新开子包）

- 是否需要层次作用域（子作用域继承父作用域的注册项）——首期可不需要，后续按实际需求加
