## Purpose

为框架引入与 Worker 解耦的**任务**承载物：一个语言无关的任务值对象（身份 / 载荷 / 状态 / 尝试次数 / 结果 / 错误 / 时间戳），以及落到既有状态机持久化作用域的**可持久化任务队列**——提交的任务随状态机落盘，进程重启后排队中的活不丢。

## ADDED Requirements

### Requirement: 任务 MUST 是身份与 Worker 解耦的值对象

框架 SHALL 提供任务值对象，其字段 MUST 至少覆盖：**身份、载荷、状态、尝试次数、结果、错误、创建时间与最近更新时间**（执行中的任务还 MUST 能给出开始与结束时间）。任务身份 SHALL 由调用方给出，且 MUST NOT 由 Worker 名字派生、MUST NOT 要求"每件活注册一个唯一名字"。任务身份 MUST 在队列内唯一可用作查询键。

#### Scenario: 任务携带身份、载荷与时间戳
- **WHEN** 构造一个任务并携带调用方给定的身份与载荷
- **THEN** 该任务的身份与载荷可读回，且创建时间与最近更新时间均被填充

#### Scenario: 任务身份不绑定任何 Worker
- **WHEN** 用同一身份的任务分别交给不同的消费者处理
- **THEN** 任务的身份保持不变，身份本身不携带、也不要求任何 Worker 名字

#### Scenario: 缺少身份的任务被显式拒绝
- **WHEN** 构造一个身份为空的任务并提交
- **THEN** 提交显式失败，队列中不产生该任务

### Requirement: 任务状态 MUST 沿明确定义的生命周期迁移

任务 SHALL 具有明确的状态集合：**待跑（pending）、执行中（running）、成功（succeeded）、失败（failed）、已取消（cancelled）**。合法迁移 MUST 为：新任务初始为待跑；待跑可被**认领**为执行中（同时尝试次数 +1）；执行中可被**完成**为成功（记录结果）或**失败**为失败（记录错误）；待跑可被**取消**为已取消；失败或执行中可被**重新排队**回待跑。除上述以外的迁移 MUST 被显式拒绝，MUST NOT 静默改写状态。

#### Scenario: 新任务初始为待跑
- **WHEN** 提交一个新任务
- **THEN** 读回该任务的状态为待跑，尝试次数为 0

#### Scenario: 认领后进入执行中且尝试次数递增
- **WHEN** 认领一个待跑任务
- **THEN** 该任务状态变为执行中，尝试次数比认领前增加 1

#### Scenario: 完成后记录结果
- **WHEN** 完成一个执行中的任务并给出结果
- **THEN** 该任务状态变为成功，结果可读回，结束时间被填充

#### Scenario: 失败后记录错误
- **WHEN** 让一个执行中的任务失败并给出错误
- **THEN** 该任务状态变为失败，错误信息可读回

#### Scenario: 非法迁移被显式拒绝
- **WHEN** 对一个已完成（成功 / 失败 / 已取消）的任务再次认领
- **THEN** 认领显式失败（返回"未认领"），该任务状态不被改写

### Requirement: 任务队列 MUST 落到状态机持久化作用域且重启不丢排队中的任务

任务队列 SHALL 存储于状态机的持久化作用域内，使队列随既有状态机持久化机制一起落盘。处于**待跑**状态的任务 MUST 在进程重启后仍然存在，且其身份、载荷、状态与尝试次数 MUST 与落盘前一致。同一队列内任务的**提交顺序** MUST 在读取与重启后保持稳定（先提交者先读回）。

#### Scenario: 提交后可按身份与状态查询
- **WHEN** 提交两个任务后分别按身份查询、按状态过滤
- **THEN** 两个任务均可按身份读回，且按"待跑"过滤得到这两个任务

#### Scenario: 重启后排队中的任务不丢
- **WHEN** 提交若干待跑任务，令状态机落盘，再用同一落盘内容重建队列
- **THEN** 重建后这些任务仍可读回，身份、载荷、状态与尝试次数与落盘前一致

#### Scenario: 提交顺序在重启后保持
- **WHEN** 依次提交身份为 A、B、C 的任务并落盘后重建
- **THEN** 按读取顺序得到 A、B、C

#### Scenario: 查询不存在的任务返回空
- **WHEN** 按一个从未提交过的身份查询
- **THEN** 查询返回"无此任务"而非抛出异常

### Requirement: 重启后处于执行中的任务 MUST NOT 被静默重跑

当进程重启时，落盘时处于**执行中**的任务其执行者已不存在，其真实结果**不可知**。队列 MUST NOT 在恢复时把这类任务**静默**改回待跑并让它被再次认领；这类任务 MUST 保持可查询（状态仍为执行中），由调用方显式决定去向。框架 SHALL 提供显式的**重新排队**入口，把执行中或失败的任务改回待跑（尝试次数不再额外递增）。

#### Scenario: 重启后原执行中任务保持可查询且不被自动重跑
- **WHEN** 一个任务在落盘时处于执行中，进程重启后用同一落盘内容重建队列
- **THEN** 该任务仍可读回且状态为执行中，且它不会被自动改回待跑

#### Scenario: 显式重新排队把执行中任务改回待跑
- **WHEN** 对上述执行中任务调用显式重新排队
- **THEN** 该任务状态变为待跑，可被重新认领，其尝试次数不再额外递增

### Requirement: 同一任务的并发状态迁移 MUST 原子生效

队列 SHALL 保证"读取-判断-改写"在并发下良定义：多个消费者以相同方式并发**认领同一任务**时，MUST 恰好一个成功、其余 MUST 得到"未认领"，且该任务状态等于成功者的结果、尝试次数只递增一次。对同一队列的并发**提交**（不同身份）MUST NOT 丢更新——提交数 MUST 等于读回的任务数。

#### Scenario: 并发认领同一任务恰好一个成功
- **WHEN** 两个消费者同时认领同一个待跑任务
- **THEN** 恰好一个认领成功、另一个得到"未认领"，该任务状态为执行中且尝试次数为 1

#### Scenario: 并发提交不同任务不丢更新
- **WHEN** 多个线程并发向同一队列提交若干不同身份的任务
- **THEN** 读回的任务总数为各线程提交数之和，无任务丢失

### Requirement: 重复受理同一任务身份 MUST 被显式拒绝

向队列提交一个**已存在身份**的任务时，队列 MUST 显式拒绝（报错），MUST NOT 静默产生第二条相同身份的任务（否则身份不再能唯一查询）。该拒绝只保证"身份在队列内唯一"，MUST NOT 被解释为投递幂等承诺——投递语义（至少一次 / 恰好一次）仍是独立的、未决的问题（issue #74），消费者幂等仍属调用方职责。

#### Scenario: 重复提交同一身份被显式拒绝且队列不变
- **WHEN** 提交身份为 X 的任务后，再次提交一个身份同为 X 的任务
- **THEN** 第二次提交显式报错，队列中身份为 X 的任务仍只有一条

#### Scenario: 拒绝不含投递幂等承诺
- **WHEN** 一个任务已被认领并完成，再提交一个身份相同的新任务
- **THEN** 队列仍以"身份已存在"显式拒绝，且框架不因该拒绝而声称对该次投递作了去重或恰好一次保证

### Requirement: 取消 MUST 只阻止尚未启动的任务且 MUST NOT 声称中断已开始的执行

取消 SHALL 只对处于**待跑**的任务生效：取消后该任务 MUST 变为已取消、MUST 不再可被认领。对处于执行中或已终态的任务，取消 MUST NOT 生效（显式给出"未取消"信号）。框架 MUST NOT 声称取消能中断或终止一个**已经开始**的执行——CPython 无法安全抢占，任务层只能承诺「不再启动尚未启动的」。

#### Scenario: 取消待跑任务后不再可认领
- **WHEN** 取消一个待跑任务，随后尝试认领它
- **THEN** 该任务状态为已取消，认领得到"未认领"

#### Scenario: 取消执行中的任务不生效且不声称中断
- **WHEN** 对一个执行中的任务调用取消
- **THEN** 取消显式给出"未取消"，该任务状态仍为执行中，且框架不声称已终止其执行

### Requirement: 未使用任务层的调用方 MUST 未见行为变化

任务层是**纯新增入口**：不调用它时，框架的既有行为（状态机读写与持久化、调度与结算、事件管道）MUST 与引入本能力前一致。新增的配置键 MUST 有"保持现状"的默认值——未配置时 MUST 不产生任何新行为；键值 MUST 在**运行期**读取（不得在模块导入期冻结默认值）。

#### Scenario: 不使用任务层时既有行为不变
- **WHEN** 一个应用只使用既有的状态机、调度与事件入口，从不提交任务
- **THEN** 其行为与引入任务层前一致，不产生任何任务队列副作用

#### Scenario: 未配置新键时取默认作用域名
- **WHEN** 配置中不含任务层相关键，直接创建默认任务队列
- **THEN** 队列落在文档化的默认作用域名上，且不改变任何既有作用域的内容
