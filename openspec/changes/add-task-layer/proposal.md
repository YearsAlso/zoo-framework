# Proposal: add-task-layer

## Why

GitHub issue #234：框架现在的执行单元是 **Worker**（一个有名字的长期槽位），不是 **Task**。于是"把一批活交给框架跑"这件事没有承载物——消费者只有两条路：给每件工作注册一个自己的 Worker（名字必须唯一），或把参数塞进事件盲投。issue 列了 5 条「建议的形状」（供讨论、非承诺）。

维护者已裁定（2026-10-14）本变更**只做前两条**：**形状 1（`Task` 值对象）+ 形状 2（落到 `StateMachine` 持久化作用域的任务队列）**。后三条（运行时容量 / 伸缩信号 / 取消语义加强）**不在本次范围内**，其中形状 3 已单独立案为 #233。

拆分理由（优先级 **架构一致性 > 业务逻辑连续性 > 开发量最小**）：形状 1+2 落在**新的任务层语义**这条接缝上（任务身份 + 可持久化的排队语义），与形状 3 的**调度器准入与池容量**是两条独立的接缝——前者可单独合入并自洽（消费者能提交、能持久化、能拉取、能结算），不依赖调度器改动。把最高风险的调度器语义变更（#233）隔离在独立变更内，评审与回滚成本最低。

## What Changes

- **形状 1（`Task` 值对象）**：新增语言无关的任务值对象，字段覆盖**身份、载荷、状态、尝试次数、结果 / 错误、时间戳**。任务身份（`task_id`）由调用方给定并**与 Worker 解耦**——同一 Worker 可消费任意身份的任务，任务不再需要"每件活注册一个名字"。
- **形状 2（可持久化任务队列）**：新增任务队列，**落到 `StateMachine` 的既有持久化作用域**——提交的任务随状态机落盘，**重启不丢排队中的活**。队列提供提交、按身份 / 按状态查询、原子认领、完成 / 失败、重新排队与最小取消入口。
- **并发正确性**：同一任务上的状态迁移 MUST 原子（并发认领同一任务恰好一个成功）；并发提交 MUST NOT 丢更新。实现复用 `StateScope` 的既有变更锁与 `compare_and_set`（A1 交付），不新造锁语义。
- **取消诚实性**：任务层只能承诺「不再启动尚未启动的」；CPython 无法抢占，**MUST NOT** 承诺能中断已开始的执行。该约束落成 spec 的 SHALL/MUST 条文。
- **默认零行为变化**：任务层是**纯新增入口**，不调用即零行为变化；新增的唯一配置键默认值保持现状（不开新行为）。
- **不改变**：`WorkerDispatchCore` 的调度语义（在飞表仍以 `worker.name` 为键、单一结算收口 `settle`、超时熔断、停机幂等）、`WorkerResult` 与结果主题、线程池背压、Worker 既有生命周期、既有状态机写入契约。

## Capabilities

### New Capabilities

- `task-queue`: 任务值对象（身份 / 状态 / 尝试 / 结果 / 时间戳）与落到状态机持久化作用域的可持久化任务队列（提交 / 查询 / 原子认领 / 完成失败 / 重新排队 / 最小取消），含并发正确性与取消诚实性契约。

### Modified Capabilities

- 无。本变更为纯新增能力，不改动任何既有能力的 Requirement（状态机的新增入口已在 A1/A2 冻结，本变更不触碰其契约）。

## Impact

- **代码**：`zoo_framework/tasks/`（新增包：`task.py` 值对象与状态、`task_queue.py` 队列）、`zoo_framework/params/task_params.py`（新增一个默认保持现状的配置键）、`zoo_framework/params/__init__.py`（导出新 params 类）。
- **配置**：新增 1 个键 `task:queue:scope`（默认 `"zoo.tasks"`）；不配置时行为与合入前一致（不新建队列、不改任何既有路径）。
- **文档**：`docs/`（新增任务层说明并入状态持久化 / 配置参考）、`docs/api/state.md`（补队列 API 指令）、`mkdocs.yml`（如新增页面则纳入导航）。
- **测试**：新增 `tests/test_task_layer.py`（值对象契约、持久化与重启恢复、认领 / 完成 / 失败 / 重新排队 / 取消、并发认领唯一性、默认零行为变化）。
- **兼容性**：纯新增入口；不使用任务层的调用方行为逐字节不变。
- **依赖**：无新增第三方依赖。
- **非目标（明确划出）**：形状 3（运行时容量：池 `resize`、`add_worker` / `submit` 与启动期同一套准入——issue #233）、形状 4（伸缩信号：队列深度驱动的策略、退避复用 `WorkerDelayManager`）、形状 5（取消语义加强）；均不在本变更，逐条落在 design.md 的 Non-Goals。
- **issue**：#234（本变更回复其中形状 1 与形状 2 的落地部分；形状 3 见 #233）。
