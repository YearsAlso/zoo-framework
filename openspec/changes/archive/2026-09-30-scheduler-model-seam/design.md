## Context

动机见 `proposal.md`。以下是塑造方案的关键现状，全部已在当前代码基上核实。

**`fix-worker-scheduling` 已实施落地**（提交 `62ae482`，spec 已合并进 `openspec/specs/worker-scheduling/`），这给了本变更一个可信地基：

| 已就绪 | 现状 |
|---|---|
| `is_loop` | 已是 `@property`，配置读取路径已统一 |
| 派发竞态 | 已消除，登记与结算由单一收口维护 |
| 超时 | 已取"观测 + 熔断"语义，`worker-scheduling` 已明确"MUST NOT 声称已终止" |
| 停机 | `BaseWaiter.shutdown(wait, timeout)` 已回收调度资源 |
| 运行期注册 | 已生效（`add_worker`） |
| 单调时钟 | 已用于内部在飞计时与停机期限（`time.monotonic()`），但**无对外时间契约** |
| 模式拒绝 | `WaiterFactory` 已对未知策略 `raise ValueError`，且已有"不可静默降级"的 spec 要求 |

**因此本变更不重复这些工作。** 它补的是三件**尚不存在**的东西：

1. 模型接缝。`BaseWaiter` 已是约 400 行的具体类，混合了三类关注点：模型无关的正确性、线程/线程池两种执行方式的细节、时间与期限的内部审计。而三个"运行策略"实际不承载任何模型差异——`StableWaiter` 只覆写 `__init__`，`SimpleWaiter` 与 `SafeWaiter` 只覆写 `call_workers`。
2. 时间契约。`time.monotonic()` 目前只服务于内部审计；`delay_time` 的语义仍是"执行完再 sleep"（`BaseWorker.run` 末尾），周期**逐轮累积漂移**；无周期/相位/抖动/截止期传播。
3. 运行标识。事件、状态作用域、日志三者之间**没有任何关联键**。

**一条必须尊重的既有决定**：`fix-worker-scheduling` 的 **D1 明确取"超时观测 + 熔断，不引入进程隔离"**。本变更不反转它（见 D7）。

**两个目标场景的约束方向相反**（见 proposal 的表）：设备线要"周期驱动 + 抖动有界"，Agent 线要"事件驱动 + 可挂起可恢复"。本变更只负责让这两者**能被声明和区分**，不实现任何一线的特化能力。

## Goals / Non-Goals

**Goals**

- 让"运行策略"真正承载模型差异：模型契约可被程序化查询，差异不再是三个文件里的偶然覆写
- 把模型无关的正确性逻辑固化为共享内核，使新增模型不必重新实现结算/超时/停机/注册
- 建立对外的时间契约：单调基准、不漂移的声明式周期、可查询的抖动、可传播的截止期
- 建立运行标识并使其贯穿事件、状态、日志三处
- **不回归** `worker-scheduling` 已生效的 8 条要求

**Non-Goals**

- 不引入进程隔离（尊 D1，见 D7）
- 不实现硬实时。本变更给的是"抖动**可观测**"，不是"抖动**有界**"
- 不实现设备线特化（协议适配、看门狗、失效安全、告警语义）与 Agent 线特化（context/state 层、工具调用协议、流式、预算策略、HITL）
- 不做 gevent 移除、`ThreadSafeDict` 换锁等性能优化——`bench/DECISION.md` 已量化为 12x–800x 并记录为**尚未分配到任何变更**
- 不引入 Rust，不改依赖列表

## 改造前的行为基线（重构 MUST 保留）

任务 1.2 的产出。抽取内核与模型时以下行为必须继续成立；`tests/test_worker_scheduling.py` 的 61 条用例是第 2–8 项的安全网，第 1、3 项需在本变更内新增覆盖。

### 三个策略的真实差异：只有一项，且与模型无关

| 策略 | 实际实现 | 池尺寸语义 |
|---|---|---|
| `SimpleWaiter` | 只覆写 `call_workers` | 池太小则**自动扩容**到 `len(workers) + 1`，从不拒绝 |
| `StableWaiter` | **只覆写 `__init__`**（无任何独有逻辑） | 严格按配置的 `pool_size`，不扩容也不拒绝（超出即排队） |
| `SafeWaiter` | 覆写 `call_workers` | 超出则抛 `ValueError`，信息里指明请增大 `worker:pool:size` 或改用 simple / stable |

**三者唯一的差异是"池尺寸不足时怎么办"，与并发原语、时间语义都无关。** 这直接印证 D2：策略名不承载模型差异，差异应降为**模型参数**（池尺寸策略）而非三个类。`SafeWaiter` 的拒绝语义 MUST 迁移而非丢失。

### 模型无关的行为（下沉到共享内核）

| # | 行为 | 现状实现 | 重构后归属 |
|---|---|---|---|
| 1 | 模式判定：显式 `worker:mode` 优先，未配置时由 `worker:pool:enable` 推导 | `get_worker_mode` | **模型选择**（新接口的一部分） |
| 2 | 未实现模式**明确拒绝**并列出已实现的模式（`NotImplementedError`） | `validate_worker_mode` + `WaiterConstant.IMPLEMENTED_WORKER_MODES` | 模型选择 |
| 3 | 池尺寸不足时的处理策略（扩容 / 排队 / 拒绝三选一） | 三个子类各自的 `call_workers` | **模型参数**（见上表） |
| 4 | 默认超时可配置，`<= 0` 表示不启用超时判定 | `self.run_timeout` ← `WorkerParams.WORKER_RUN_TIMEOUT` | 共享内核 |
| 5 | 超时熔断后的 Worker 不再被派发 | `self._broken: set` | 共享内核 |
| 6 | 在飞表与熔断集合由**单一 `threading.RLock`** 保护 | `self._lock`（派发线程与完成回调并发访问） | 共享内核（并发契约） |
| 7 | 结果响应器绑定到**统一结果主题**，且重复构造调度器不堆积 | `register_handler` → `bind_topic_reactor(WaiterConstant.WORKER_RESULT_TOPIC, ...)`（绑定已具幂等语义） | 共享内核（结果投递） |
| 8 | 停机标记 | `self._stopped` | 共享内核（停机） |

**第 7 项特别重要**：这是"结果投递曾经完全失效"（主题不匹配、线程模式不上报）修复后的形态，重构中极易被破坏——它是 61 条用例里 `TestResultReporting` 那组的对象。

## Decisions

### D0 · 按"同一框架、两种调度模型"设计，不拆产品线（**须确认**）

这是尚未被回答的上游决定。本方案按"同一框架双模式"成立，理由是**它在两个方向上不对称、可逆性不同**：

- 若先做接缝、日后要拆产品线 → `SchedulerModel` 边界**正好就是拆分线**，接缝的投入不会浪费
- 若先拆产品线 → 共用部分（事件管道、状态、参数、CLI、打包、CI）立刻分叉，且不可逆

所以"先做接缝"在任何一种最终选择下都是对的，而"先拆产品线"只在一种选择下才对。**若最终决定双产品线，本变更的接口与 spec 均不变**，只是打包与文档分家。

### D1 · 接缝切法：抽出「共享内核 + 模型接口 + 模型实现」三方

- **选**：把 `BaseWaiter` 拆为
  - `WorkerDispatchCore`（共享内核）：单一结算收口、超时观测与熔断、停机资源回收、运行期注册——即四类**模型无关**的正确性逻辑
  - `SchedulerModel`（接口）：声明并发原语、时间语义、背压策略、停机语义、支持的 Worker 类别、可观测指标
  - 模型实现：本变更至少两个（周期驱动 / 事件驱动）
- **理由**：现状是"一个具体类 + 三个空壳子类"，模型差异无处声明；而三类关注点混在一起使任何模型新增都必须复制 400 行。
- **已考虑的替代**：① 保持 `BaseWaiter` 为具体类、只在子类加差异——拒绝，那正是现状；② 一步到位引入独立包——拒绝，范围与收益不成比例。
- **最硬的约束**：`worker-scheduling` 的 8 条要求 MUST 全部继续成立。唯一可靠的手段是**先把那 8 条对应的行为固化为回归用例，再重构**（任务 1 先于一切重构）。

### D2 · 模型按「并发原语 × 时间语义」两维声明，simple/stable/safe 退场

- **选**：模型契约的两维取值为：并发原语（线程 / 线程池 / 事件循环 / 进程）与时间语义（周期驱动 / 事件驱动）。`进程` 作为合法取值存在但**未实现**，请求时 MUST 明确拒绝（延续"不可静默降级"）。现有 simple/stable/safe 的差异（池大小、是否重建 worker 列表）属**参数**，降为配置。
- **理由**：这两维正是两条目标线的分岔点；用策略名承载模型差异会让"名字"与"语义"脱钩。
- **BREAKING**：`SimpleWaiter`/`StableWaiter`/`SafeWaiter` 退场。`SafeWaiter.call_workers` 现有的"worker 数超过池大小即拒绝"行为 MUST 迁移为模型的显式参数校验，MUST NOT 在重构中丢失。
- **已考虑的替代**：保留三个策略名各自声明模型——拒绝，会出现"同一模型两个名字"或"两个名字一个模型"的混乱。

### D3 · 标识传播：显式字段为真相来源，上下文变量仅作便利读法

- **选**：`run_id`/`session_id` 作为 `WorkerResult`、`EventNode` 与运行期对象的**显式字段**（真相来源）；同时提供上下文访问器（`contextvars.ContextVar`）供不便改签名的调用点读取，且**派发到工作线程时必须显式 `copy_context`**。
- **理由**：只靠 `ContextVar` 在本框架的主执行路径上会**静默丢标识**——`ThreadPoolExecutor` 提交的任务不会继承调用方的 `ContextVar` 上下文，而主路径恰好是跨线程派发。这会直接违反 spec 的"跨越线程传播"要求，且是静默失效。纯显式传递则侵入面过大。
- **已考虑的替代**：只用 `ContextVar`（拒绝：跨线程静默丢，正是 spec 禁止的失效模式）；只用显式参数（拒绝：改签名面过大）。
- **这条是本次最容易踩的坑**，故在任务中单列一条"并发不串号"的验证。

### D4 · 周期排期：单调时钟绝对序列 + **跳过**错过的轮次（不补跑）

- **选**：以单调时钟的绝对序列（基准 + n×周期）计算每次触发时刻。单轮执行超过周期时，MUST **跳到下一个未来时刻**并计数"跳过次数"，MUST NOT 补跑积压轮次。
- **理由**：补跑在高负载下会**雪崩**——积压轮次越补越多。设备控制里"迟到的控制输出"不如"错过并如实报告"；跳过是可观测的（跳过次数与抖动都进指标）。
- **已考虑的替代**：catch-up 补跑（拒绝，雪崩不可接受的失效模式）；保持"执行完再 sleep"（拒绝，那正是现状漂移）。若某业务确实需要补跑，由 Worker 自身在其执行体里处理。
- **必然产物**：跳过次数成为模型指标集的一部分。

### D5 · 抖动在模型内埋点，Worker 不参与

- **选**：模型在触发前记录理论时刻与实际触发时刻，Worker 不参与抖动测量。
- **理由**：抖动是**调度质量**指标而非业务指标；若由 Worker 自报，Worker 自身的启动开销会污染测量。事件驱动模型没有抖动，需模型层显式返回"不适用"（spec 已要求 MUST NOT 以 0 代替）。

### D6 · 截止期双通道：事件字段 + 运行期可读属性

- **选**：截止期同时作为 `EventNode` 的字段（跨层传递载体）与运行期对象的可读属性（Worker 内直接读取）。
- **理由**：spec 要求"随事件传递到最终执行的 Worker"；事件是跨层载体，Worker 需要直接可读。只放其一都不满足。

### D7 · 明确不反转 D1：不引入进程隔离，也不承担 gevent 移除

- **选**：本变更不引入进程宿主。并发原语的"进程"取值**声明存在但请求时明确拒绝**。
- **理由**：`fix-worker-scheduling` 的 D1 已定案"观测 + 熔断，不引入进程隔离"。进程宿主涉及 supervisor、IPC、序列化边界与失效安全，是**设备线的独立技术选型**；把它混进接缝变更会让"接口设计"与"隔离设计"互相绑架。同理，gevent 移除与 `ThreadSafeDict` 换锁属 `bench/DECISION.md` 记录的四项独立优化，本变更只要求模型**声明**其并发原语。

## Risks / Trade-offs

**[重构回归 `worker-scheduling` 的 8 条要求] → ** 这是本变更最主要的风险：接缝抽取动的是刚修好的调度内核。缓解：任务 1 先为那 8 条要求各写回归用例并确认全绿，之后每次重构都以该套用例为准；任何一条转红即回退该步。

**[`SimpleWaiter`/`SafeWaiter` 退场影响下游] → ** 直接构造它们的外部代码会失败。缓解：`WaiterFactory` 的拒绝路径已会明确报错（已落地行为），错误信息必须列出可选模型名（spec 已要求）；同时 `SafeWaiter` 的池大小校验 MUST 迁为模型参数，MUST NOT 丢失。

**[周期语义变更使依赖旧漂移行为的下游观察到差异] → ** 已在 proposal 标 BREAKING。缓解：不引入新 API 的情况下无法完全避免；把"跳过次数"作为显式指标暴露，使差异可被观测而非莫名其妙。

**[跨线程 `ContextVar` 静默丢标识] → ** 会直接违反 spec 且难以发现。缓解：D3 定下"显式字段为真相来源"，并在任务中单列"并发执行不串号"与"工作线程内可访问"两条验证。

**[抖动测量本身引入开销] → ** 每次触发都要记两次时间戳。缓解：只做内存内数值记录，MUST NOT 在每次触发写日志或落盘；抖动样本按固定窗口保留（窗口大小见 Open Questions）。

**[`bench/DECISION.md` 的四项优化仍未分配] → ** 它们量级 12x–800x，远大于本变更的任何收益，却仍无变更承接。缓解：本变更**不**顺手做（会扩大范围），但在任务中加一条显式核对——确认它们已进入某个变更或明确排期，避免"又一次被漏掉"。

**[接受"抖动不可承诺"这一局限] → ** 本变更只能给可观测的抖动，不能给有界抖动。若设备线最终要求硬实时，需要另立变更，且可能推翻现有线程模型。缓解：在 proposal 与 design 中均已明写，不让"抖动可观测"被误读为"实时性已满足"。

## Open Questions

以下三项**不影响 spec、方案与任务拆分**，可在实现期决定：

- **模型的具体命名**（如 `ThreadPoolPeriodicModel` / `EventDrivenModel`）——命名不进入契约语义。
- **抖动样本的保留窗口**（最近 N 次 vs 全量）——spec 只要求"最近一次 / 上界 / 样本数"三项必得，窗口大小是内存与信息量的权衡。
- **`run_id` 的载体形式**（UUID vs 进程标识 + 单调序号）——spec 只要求"唯一且在运行期间不变"。
