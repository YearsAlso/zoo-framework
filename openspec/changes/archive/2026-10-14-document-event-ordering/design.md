# Design: document-event-ordering

## Context

见 proposal.md。事实链：`EventFIFO` 是每通道独立的队列（`list` 语义）→
`EventWorker._execute` 按弹出顺序取事件 → 每个事件的 `reactor.execute` 提交给
实例级 `ThreadPoolExecutor(max_workers=event:executor:workers)` → 同一响应器的多次调用
在池内重叠 → 完成顺序 = 实际完成顺序。批量路径（`event:dispatchBatchingEnabled=true`）
把同 (channel, reactor) 同轮事件聚成一个 callable（`_run_batch`），批内**顺序**逐个
`execute`，因此恰好给出了串行语义，但它是**进程级**开关，且默认关闭。

## Goals / Non-Goals

**Goals**
- 把"FIFO 只保证投递顺序、不保证完成顺序"写进规格与消费侧类说明，消除未文档化的惊喜
- 同时写明"需要顺序完成"的两条出口（自行串行化 / 批量投递）与后者的代价（进程级开关）
- 用可执行断言锁住真实语义，防止文档与行为漂移

**Non-Goals**
- 不改运行时并发形态（并发是有意为之：性能导向，且被 issue 承认为"性能导向，现在的实际行为"）
- 不新增按响应器 / 按主题声明串行的配置入口
- 不改优先级、重试、去向、响应器查找语义

## Decisions

### D1: 判定为"文档缺陷"而非"行为缺陷"，因此不改行为

判定依据见 proposal 的三条事实。若把完成顺序改成 FIFO，需要"同响应器串行"或
"按入队顺序回收结果"，前者牺牲吞吐（回应器的并发是刻意的），后者需要一个跨事件的
顺序回收器——两者都是**新功能级**的设计变更，且 issue 明确说"两个都说得通，但需要
明确其中一个"。故本变更只把现状写成契约。

### D2: 规格落点选 `event-dispatch` + `event-dispatch-batching` 两条

顺序语义横跨两条既有规格：逐事件路径的顺序承诺在 `event-dispatch`（消费路径），
串行出口在 `event-dispatch-batching`（批量的顺序不变条款）。只改一处会留下另一半
含糊表述——特别是 `event-dispatch-batching` 的"通道内处理顺序（仍按弹出顺序执行响应器）"
最容易被读成完成顺序，必须澄清。

### D3: 文档落点选 `EventWorker` 类说明（而非 `docs/` 站点）

类说明就是消费侧最靠近使用者的文档（且现有 join-timeout 语义也写在同处，位置一致）；
`docs/` 站点的事件一节归其他所有者，本变更不越界，列入协作事项。
`EventWorker` 属公开导出面，按仓库既有 `api-docstring-english` 约定，新增段落用英文，
行注释用中文。

### D4: 测试形态是"特性锚定 + 文档锚定"，不是"先红后绿"的行为回归

本变更无行为改动，因此不存在"修复前失败"的行为用例。可执行断言分两半：
① 行为锚定（出队顺序 = 入队顺序；缺省路径完成顺序 ≠ 入队顺序；批量路径串行），
② 文档锚定（类说明含 delivery / completion order 的声明）。②在合入前**确实为红**
——这正是"未文档化"这一缺陷的回归守卫。

## Risks / Trade-offs

- [文档固化并发语义，未来若改为串行会与规格冲突] → 这是有意的：规格是承诺，改承诺
  必须改规格（本变更正是把隐性行为提升为显性承诺）。
- [用 sleeping 响应器断完成顺序的用例可能受机器负载影响] → 用 0.4s / 0.01s 的大间距，
  且断言的是"完成顺序由完成时刻决定"这一本质；线程池 8 线程下两者并发启动，
  快者必然先完成。
- [批量路径被当成"顺序保证"的替代品] → 规格明说它是**进程级**开关、会改变所有通道的
  执行形态，与"只想让某个主题按顺序"的成本不对称（issue 的补充信息即此痛点）。

## Migration Plan

1. 合入即生效：行为零变化，仅规格与文档补齐
2. 需要顺序完成的调用方：自行串行化（推荐，作用域可控）或全局开启批量投递
3. 回滚 = revert 单个变更提交

## Open Questions

1. **是否应提供"按响应器（或按主题）声明串行"的入口？**（issue 的方向 ②）
   需要维护者裁决：这是新增功能与设计分歧（配置面位置、与批量投递的关系、
   是否引入第三处"顺序真相源"），本变更不自行拍板。
2. **注册名/实例名的顺序歧义（与 #229 同源）**：见 `fix-result-reactor-name-filter`
   的 Open Questions，是否引入独立实例标识同属命名方案层面的裁决项。
