## Context

动机见 `proposal.md`。以下是塑造方案的关键事实。

**一处假断言**：`scoped-container` 归档进基线的「框架自身的进程级共享 MUST 被显式归类」含全称句 `MUST NOT 依赖隐式的全局单例状态`，而 `WorkerRegistry._global_registry` 与两个类级注册表（`reactor_map` / `_channel_map`）**正是**隐式全局单例状态。实现没做错——该变更的范围自始是 8 处 `@cage` 使用点；错在规范句写成了全称。旁证：同一 Requirement 的两个 Scenario 只点名已迁入容器的那批，**规范句绝对、场景窄**。

**三处基线缺口**：`exclusive` 的入口契约未写；原型级语义空白；声明只须"存在"、无须"为真"。

**一处已核实的关键分量**：第三条缺口不是形式问题。清点时 `EventRegister`（裸 `list`）与 `WaiterResultReactor`（执行期读可变字段）两处不对，实现据此把归属声明为 `SINGLE_THREAD` 而**不是** `INSTANCE_GUARANTEED`——因为**一个为假的声明比不声明更糟**，它把未验证的安全假设写进代码。该判断在实现里成立，在基线里无依据。

## Goals / Non-Goals

**Goals**

- 让基线中每一条要求对现状**为真**——不留下"字面为假"的要求
- 把已知欠债**显式记录**，使其不被误读为已满足，同时不掩盖
- 补齐三处缺口，且补法本身要抵抗漂移

**Non-Goals**

- 不迁移残留的隐式全局单例（另一个变更；且类属性与实例的收编量级不同）
- 不改变任何运行时行为

## Decisions

### D1 · 收窄而非收编：把全称断言限定为"新引入的"，并把欠债写进基线

- **选**：原句的 `MUST NOT 依赖隐式的全局单例状态` 收窄为 `MUST NOT 依赖**新引入的**隐式全局单例状态`；同时在同一条要求里显式列出已知欠债（`WorkerRegistry._global_registry`、两个类属性）并要求它们 MUST 被记为欠债、MUST NOT 被表述为已归类、MUST 带承接锚点。
- **理由**：
  - "不新引入隐式全局单例"这一**面向未来**的保证是可成立的，且那才是原句真正想守的东西；保留它就把有价值的约束留下了。
  - 只收窄而不记账，读起来像**把门槛降到刚好通过**；只开收编变更而不先收窄，则基线在那之前**一直断言着一件为假的事**。两件一起做，基线既不假、也不掩盖。（此判断来自与并行会话的复查讨论。）
  - 收编本身不适合搭便车：`reactor_map` / `_channel_map` 是**类属性**，没有实例身份，"把它注册进容器"之前要先回答"它是谁的字段"——与把实例注册进容器不是同一种改动，量级须分开估。
- **已考虑的替代**：① 直接开变更收编残留——拒绝，量级不同且会让本次的"基线为假"状态多延长一个变更周期；② 只改基线不记账——拒绝，理由如上。

### D2 · 原型级语义用「单一性质 + 派生后果」表述，而不是并列四条独立断言

- **选**：要求写成"原型级的语义 MUST 由**一条性质**确定：**解析结果不被容器缓存**"，其余行为（每次新建、查询为空、释放无销毁动作、替换仍生效）MUST 表述为**由该性质派生**的后果。
- **理由**：这四条**本就派生自同一性质**（源码里 `container.py` 的注释也这么写：「原型级本就不缓存，没有可丢的实例」）。写成四条并列断言，等于给未来埋一个漂移点——改了一条忘了另一条，而**那正是本仓库正在修的缺陷类型**。单一性质把可漂移面从四处收敛到一处。
- **已考虑的替代**：并列四条独立断言——拒绝，理由如上；这不是风格偏好，是可维护性直接相关的取舍。
- **附带的好处**：审查者只需验证一条性质，不必分别验证四条；将来"不缓存"若变，改动点唯一。

### D3 · 「声明须如实」的可核对形式：依据写在代码里 + 用例固定该声明

- **选**：要求写明"声明的取值 MUST 与实例实际行为相符；对既不加锁、又可能在执行期被无栅栏读写的实例，MUST NOT 声明为『由实例自身保证』，MUST 声明为『仅限单线程』"，并要求"判定依据 MUST 在代码中可核对，且 MUST 有用例固定该声明"。
- **理由**：纯粹的"必须如实"无法机械验证，写进基线只会是一句无人能核的口号。**把可核对的部分固定下来**——依据在代码里写明（哪一处字段、为什么不算自保）、用例把声明钉死在 `SINGLE_THREAD`——就把一句无法验证的约束变成了两条可检查的断言，同时挡住了"将来有人把这两处静默『升级』为 `INSTANCE_GUARANTEED`"这条最现实的退化路径。
- **已考虑的替代**：① 只写"必须如实"——拒绝，不可核对；② 试图写一条自动检测"声明是否属实"的规则——拒绝，那需要判断任意实例的线程安全性，不可判定。

### D4 · 本变更不改运行时行为

- **选**：除两处 `SINGLE_THREAD` 声明处补写依据注释、以及新增固定声明与补齐语义的用例之外，不动实现。
- **理由**：三条新增要求描述的都是**既有行为**（`exclusive` 的三条语义、原型级的四条后果，实现里都有且已有用例覆盖）。本变更是**把既有事实写进基线**，不是新定行为——一旦掺入行为改动，"补文档"就会变成"改语义"，两者的验证强度完全不同。
- **披露**：`exclusive` 的既有用例已覆盖块内串行、可重入与返回真实实例；本次另请并行会话做一次**独立实测**（不依赖我的用例）作为旁证，因为"我的用例恰好没测到"是一个真实存在的风险类别。

## Risks / Trade-offs

**[收窄措辞可能被读成"放宽要求"] → ** 缓解：收窄只针对**时态与范围**（"框架内部的"→"新引入的"），同时把欠债从"默默不满足"变成"显式记账并带锚点"。判断标准是：改后每一句都对现状为真，且没有任何一条把欠债说成已满足。

**[记账可能被当成"已经处理了"] → ** 缓解：要求里写明这类载体 MUST NOT 被表述为已由容器归类，且 MUST 带承接锚点。若后续无人承接，锚点是可见的悬空项，而不是一条被遗忘的注脚。

**[新增要求与既有实现不符] → ** 缓解：三条新增要求逐条对照实现与既有用例后才落笔（原型级四条已由并行会话独立实测；`exclusive` 三条既有用例覆盖、另请独立实测）。这是本次要修的缺陷的对偶面——写要求时同样不能断言未验证的事。
