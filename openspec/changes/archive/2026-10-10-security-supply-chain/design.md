## Context

见 `proposal.md` 的 *Why*（#89–#95 的实际状态从未被记录；"钉 SHA"有漏项；加固只在 dev 生效；
使用者没有可读的安全说明）。本设计只需要补充**影响做法的当前约束**：

- **默认分支落后**：`main` 落后 `dev` 88 个提交，`git diff --stat origin/main..HEAD -- .github/`
  = 8 文件 +226/−55。`main` 上 7 个 workflow 只有 3 个声明了顶层 `permissions`、全部 action
  用 tag、没有 `codeql.yml` / `dependabot.yml`，且仍带 2023 年的 `requirements*.txt`。
  issue #107 正在处理这条分支滞后，其 design 要求先在 a/b/c 三种策略里选定一种。
- **外部审计只看默认分支**：Scorecard 的采样对象是 `main`（`--change` 无关）。本变更能改的
  只有开发线，**分数不会因为本变更立刻变化**。
- **`docs/` 的读者分工**：自 `0.10.6-beta` 起，面向使用者的站点是另一个仓库
  （`zoo-framework-doc`）；仓库内 `docs/` 的定位是维护者/贡献者文档，但仍由 mkdocs 发布到
  仓库自己的文档站（nav 里同时有 tutorial/guides）。issue 指定的 `docs/SECURITY_MODEL.md`
  路径因此保持不动，只在文内写清它的读者。
- **发布路径只能在 tag 推送时执行**：`release.yml` 的发布作业本地无法端到端验证，可验证的
  只有静态事实（权限声明、是否传长期 token、是否钉 SHA）与外部产物（PyPI 上的证明）。

## Goals / Non-Goals

**Goals:**

- 把 #89–#95 的**实际状态**变成一份带证据、可复核、能区分分支生效范围的留档。
- 把"钉 SHA""顶层权限""OIDC 发布""锁文件同源""支持版本表不漂移"变成 CI 能拦的断言。
- 给使用者一份四节齐备、并把"未做的事"写清楚的安全说明。

**Non-Goals:**

- **不**修 `main`：不推分支、不开定向 PR、不做 `dev`→`main` 合入（#107 范围）。
- **不**申请 OpenSSF Best Practices 徽章（#95，仓库外的问卷动作）。
- **不**动 `zoo_framework/` 运行时行为、不新增第三方依赖、不调整 release 作业的逻辑，
  只钉两处漏掉的 SHA。
- **不**为了 Scorecard 分数删掉合法的作业级写权限。

## Decisions

### D1 状态表的落点，与"实际生效"的定义

**决定**：新增独立文档 `docs/security-supply-chain.md` 并加入 mkdocs nav。"实际生效"
一律以**默认分支**为准——同一项同时标出「开发线已落地」与「默认分支尚未生效」，并指向
跟踪 issue。

**理由**：默认分支是外部（搜索引擎、徽章、任何点进仓库的人）看到的那个；只写"dev 已做"
就是本 issue 要消灭的那种"以为做了"。

**备选**：并入 `docs/SECURITY_MODEL.md`（把 CI 内部台账混进使用者说明，读者视角是噪音）；
只留在 change 与 issue 评论里（不留档，后人要翻归档，且无法机械校验）。

### D2 支持版本表去漂移：连举例一起去掉

**决定**：`SECURITY.md` 的支持表改为不含任何当前版本线字面量的表述；机械断言禁止表中
出现 `数字.数字`（固定边界 `1.0` 除外）并禁止出现 `pyproject.toml` 的当前版本串。

**理由**：dev 的表虽然已经不写死"支持 0.5.x"，但**举例**仍是 `0.9.x` / `0.8.x`，而项目已是
`0.10.x`——举例同样会漂移，而且很难在 bump 时被想起。把断言做成"表里不许有版本号"，
比"记得同步举例"可靠。

**备选**：保留举例、每次 bump 同步（人工，必然漂）；用 `<major>.<minor>.x` 占位符（读者需要
从别处推算，且可读性换来的只是同一条人工纪律）。

### D3 `main` 的陈旧支持版本表交由 #107，本变更只验证并留档

**决定**：`main` 上的 `SECURITY.md` 不动；本变更产出 main↔dev 的实测对照与防漂移断言，
并在状态表中把该项标注为"默认分支尚未生效（#107）"。

**理由**：#107 自身要求先在 a/b/c（回并文档提交 / 换默认分支 / 自动回并）之间选定策略；
本变更单点改 `main` 会绕过那个决策，且若 #107 选"换默认分支"，动作会作废。

**附带事实（决定了此举无副作用）**：本变更的机械断言随文件一起只存在于开发线。
`main` 上还没有 `tests/test_security_supply_chain.py`，因此 **`main` 的 CI 不会因此变红**——
这个声明只在 #107 把开发线合并过去时与文件一同到达，届时 `SECURITY.md` 也已同步。

**备选**：向 `main` 开一个只含 `SECURITY.md` 的定向 PR（能立刻消灭默认分支上的错误信息，
但绕过 #107 的决策，且需要额外授权）；一并做 `dev`→`main` 合入（会触发 `main` 上的 minor
稳定版发布，属发版决策，远超本 issue 范围）。

### D4 钉 SHA 的漏项直接修，复用同文件已在用的 SHA

**决定**：把 `release.yml:364` / `:384` 的 `actions/checkout@v4` 钉到
`11d5960a326750d5838078e36cf38b85af677262  # v4`——即**同一文件 `:425` 已经在用**的那个
commit SHA，不引入新版本、不引入新来源。

**理由**："全做或不算做"是这项检查的性质：一个未钉的引用就足够完成投毒。复用同文件已有
的 SHA 把改动面压到最小（两行），也避免出现"同一 action 在同一文件里钉到两个不同 SHA"。

**备选**：整体升级到更新的 checkout 版本（需要重新核 SHA 与行为差异，超出本 issue）；
保持现状并在文档里如实记录（钉 SHA 那一项就永久是"部分落地"，没有理由接受）。

### D5 不追加 `actions/attest-build-provenance`

**决定**：不新增 GitHub 原生 attestation 步骤，如实记录来源证明已由 trusted publishing
产出。

**理由（实测，非推断）**：PyPI integrity API 对本项目已发布的 `0.10.0` 的
**wheel 与 sdist 都返回 200**，载荷是 Sigstore 签名的 in-toto 证明（PEP 740），其中含产物
的 sha256。也就是说 attestation 已经存在且可外部核对；再加一个 GitHub 原生步骤的收益是
`gh attestation verify`，代价是一条**只能在 tag 推送时**才被验证的发布路径步骤——多一条
发布期失败点，换一份等价信息。

**备选**：加原生 attestation（收益如上述；风险为不可本地验证的发布路径新增步骤）；
同时保留 SBOM + `cosign` 签名（现状已是两者都有，无需取舍）。

### D6 能静态判定的一律做成 pytest，需要网络的写成可复跑命令

**决定**：pytest 只做**离线可判定**的断言——钉 SHA、顶层权限、OIDC 声明、不传长期 token、
无第二份依赖清单、锁文件与 pyproject 同源、版本表去漂移、文档结构/nav、未做事条目、
支持表双语一致。需要网络或发布才能验证的（PyPI 证明、Scorecard 分数、徽章状态）写进
状态表作为**可复跑的复核命令**，不进测试。

**理由**：测试在 CI 三平台跑且应当离线可复跑；把网络请求写进测试会带来假红（限流、
被墙、上游改接口），而"分数是多少"本来就是快照，不适合做恒等断言。评分快照以
采样时间 + commit 的形式留档，谁都能复跑核对。

**备选**：把 Scorecard 查询写成测试（假红风险 + 与上游接口耦合）；完全不记录分数（回到
"靠猜"）。

### D7 `RELEASE_PAT` 长期凭据：如实披露，不在本变更删除

**决定**：状态表与安全模型文档如实写明：发布**不**使用长期 token（OIDC），但自动回并的
机器人 PR 仍使用长期 `RELEASE_PAT`；不删除它。

**理由**：`peter-evans/create-pull-request` 需要 PAT 才能让开出的 PR 触发后续 workflow
（`GITHUB_TOKEN` 创建的 PR 不触发），删除会打断既有的版本线自动回并流程
（`fix-release-version-continuity`）。这属于"已知的、有理由的例外"，如实写出来比删掉更
有用。

**备选**：改用 GitHub App 令牌（更复杂，超出本 issue）；删除 PAT（会打断回并流程）。

## Risks / Trade-offs

- **文档与断言双真源漂移** → 断言的输入全部取自仓库文件（workflow / pyproject / 锁文件），
  文档引用同一批路径与行号；凡断言覆盖的事实（钉 SHA、顶层权限、锁文件同源、版本表），
  二者不一致即 CI 红。
- **`release.yml` 的改动无法本地端到端验证** → 只改两行、复用同文件已在用的 SHA、
  不改步骤逻辑与顺序；静态断言覆盖"全部 `uses:` 已钉"这一性质。
- **状态表会随时间过时（分数、行号）** → 表内固定记录采样时间与被采样 commit，并写明
  复核命令；行号漂移会被断言间接暴露（断言不依赖行号，只依赖性质）。
- **`docs/SECURITY_MODEL.md` 与另一个文档站的分工** → 文内写明读者与站点分工，不改动
  另一个仓库；路径按 issue 指定保持在 `docs/`。
- **分数不会因本变更立刻上升** → 在状态表中明确写出：分数是默认分支的快照，本变更改变的是
  开发线的性质与留档质量，分数变化要等 #107 合并。

## Migration Plan

无迁移：本变更不改运行时行为、不改配置键、不改持久化格式。回滚即为 revert 本次提交
（文档、两行工作流、一个测试文件）。
