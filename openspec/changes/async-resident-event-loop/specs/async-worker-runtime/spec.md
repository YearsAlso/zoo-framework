# async-worker-runtime 规格变更（async-resident-event-loop delta）

## ADDED Requirements

### Requirement: 异步 Worker 的驱动路径 MUST 由执行模型决定

异步 Worker 的异步执行体 SHALL 由当前执行模型决定如何驱动，MUST NOT 由 Worker 自行假定"所在线程没有运行中的事件循环"。执行模型为常驻事件循环时，Worker MUST NOT 自建并关闭事件循环（自建会让常驻循环形同虚设，并把"每次派发建一个循环"的开销留在热路径上）；执行模型为线程或线程池时，既有"在工作线程内直接驱动协程"的行为 SHALL 保持不变。模型决定驱动路径这一事实 MUST 可在运行期被观察到（同一次执行在两条路径下的循环创建次数可区分）。

#### Scenario: 常驻循环模型下不自建循环

- **WHEN** 一个异步 Worker 在常驻事件循环的模型下执行多次
- **THEN** 整段执行期间事件循环的创建次数为一次（复用同一个常驻循环），而非每次执行一次

#### Scenario: 线程模型下行为不变

- **WHEN** 一个异步 Worker 在线程或线程池模型下执行
- **THEN** 其异步执行体仍被调用并回传业务返回值，行为与既有实现一致

### Requirement: 常驻事件循环的生命周期 MUST 由执行模型持有且停机 MUST 幂等

常驻事件循环 SHALL 由执行模型在其容器启动时创建、在容器回收时关闭，MUST NOT 由 Worker 或调用方各自持有。停机时 MUST 先使新派发被拒绝，再在给定界内等待在飞协程结算，最后停止并关闭循环；MUST NOT 在在飞协程尚未结算时关闭循环（否则结算与结果投递永不发生）。停机 MUST 可重复调用且 MUST NOT 抛出异常；关闭后的循环 MUST NOT 再接收新任务。

#### Scenario: 停机后不再接收新任务

- **WHEN** 常驻循环模型的调度器已完成停机，随后再次派发一个异步 Worker
- **THEN** 该派发被拒绝，且不产生"提交成功但永不执行"的静默悬挂

#### Scenario: 停机前在飞协程仍被结算

- **WHEN** 停机发生在若干协程仍在执行时
- **THEN** 这些协程在界内被等待并完成结算（其结果照常投递），循环随后才被关闭

#### Scenario: 重复停机安全

- **WHEN** 对常驻循环模型的调度器连续调用两次停机入口
- **THEN** 两次均不抛出异常，循环线程被回收且不残留
