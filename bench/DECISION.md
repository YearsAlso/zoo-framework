# go / no-go 决策

**变更**：`adopt-rust-core`（P2：PoC + 测量 + 决策）
**结论**：**no-go** —— 针对框架当前的形态（派发 Python 执行体并收回完成信号）。
实测加速比上限 1.67x、典型档位 1.0–1.2x，不足以支撑引入 Rust 的成本。
**例外**：若目标是一个真正的 **Server 运行时**（Rust 全程处理连接，Python 只在请求
到达时被调用），那是另一种架构，**本次 PoC 未测量**，需要单独验证。

---

## 一、两个决定性数字

### 1. 框架自身开销（任务 6.1 / 6.2）

Windows 实测，代表性负载（`bench/workload.py`），执行体耗时在同一次运行内埋点测得：

| 档位 | Worker 体 | 端到端 | **框架开销** | **占比** |
|---|---|---|---|---|
| cpu-1x | 0.039 ms | 0.133 ms | 0.094 ms | **70.76%** |
| cpu-10x | 0.289 ms | 0.391 ms | 0.102 ms | **26.12%** |
| cpu-100x | 2.734 ms | 2.858 ms | 0.124 ms | **4.34%** |
| io-10ms | 10.332 ms | 10.551 ms | 0.219 ms | **2.08%** |

**框架开销稳定在 94–220 µs**；占比随执行体变长从 70.76% 掉到 2.08%。

> **平台说明**：本表是 Windows 数据。Linux 侧只能在 WSL2 上取数，而 WSL2 测出
> 328–432 µs（约 3 倍），这是 Hypervisor 放大跨线程唤醒延迟造成的伪影——与 design D0
> 的警告一致。**该绝对数字不用于决策**，仅印证"占比随执行体变长而下降"这一形状。
> 原生 Linux 的取数需要 CI 的 `ubuntu-latest`（见「未完成项」）。

### 2. PyO3 边界成本（任务组 3）

| 项 | Windows-AMD64 | Linux-x86_64 |
|---|---|---|
| Python→Rust 空调用往返 | 28.9 ns | 23.9 ns |
| Rust→Python 回调（持 GIL） | 63.5 ns | 48.2 ns |
| `allow_threads` 往返 | 63.9 ns | 63.4 ns |
| 纯 Python 空调用（参照） | 27.4 ns | 20.8 ns |
| 粗细粒度比值（1000 件事） | 32.5x | 23.1x |

**边界穿越 28.9 ns 与纯 Python 空调用 27.4 ns 几乎相同——穿越成本可忽略。**
这修正了 design D2 原先引用的 0.33 µs（ctypes 上界），高估了约 11 倍。

## 二、Rust 能拿回什么 —— **实测，不是估算**

实测方式：实现最小 Tokio 调度器（`pyo3_probe.RustDispatcher`），与框架当前的调度路径
做同机对照。两侧使用同一份执行体、同一份输入、同一套唤醒机制（`threading.Event.set()`）。
Rust 侧**不实现**任何调度语义（无超时熔断、无在飞表、无结果聚合）——它测的是这条链路的
**下界**。脚本：`bench/compare_execution_models.py`。

### 端到端延迟对照

| 档位 | Python 端到端 | Rust 端到端 | **加速比** |
|---|---|---|---|
| cpu-1x（执行体 ~46 µs） | 0.1589 ms | 0.0950 ms | **1.67x** |
| cpu-10x（执行体 ~0.31 ms） | 0.4159 ms | 0.3417 ms | **1.22x** |
| io-10ms（执行体 ~10.3 ms） | 10.5597 ms | 10.4958 ms | **1.01x** |

### 框架开销对照

| 档位 | Python | Rust | 加速比 |
|---|---|---|---|
| cpu-1x | 0.1127 ms | 0.0508 ms | 2.22x |
| cpu-10x | 0.1079 ms | 0.0518 ms | 2.08x |
| io-10ms | 0.2165 ms | 0.0666 ms | 3.25x |

**这推翻了本变更早期的估算。** 原先估计 Rust 化后框架开销可降到 ~25 µs、整体 3–5x；
实测 Rust 侧开销是 **51–67 µs**，且**不含任何调度语义**——加上真实的超时判定、在飞表
维护与结果聚合后还会更高。

**为什么 Rust 侧开销没有降到预期的量级**：这条链路里两次 `Python::with_gil` 获取
（执行体一次、完成回调一次）与主线程唤醒是主导成本，而它们**不是调度实现问题**。
边界穿越本身只要 29 ns——瓶颈在 GIL，不在调度。

### 跨平台一致性（任务 5.5）

| 档位 | Windows 加速比 | Linux(WSL2) 加速比 |
|---|---|---|
| cpu-1x | 1.67x | 2.15x |
| cpu-10x | 1.22x | 1.56x |
| io-10ms | 1.01x | 1.04x |

**两个平台的结论方向一致，无反转**：加速比在细粒度档最高（1.7–2.2x），随执行体变长
迅速衰减到 1.0x。

## 三、结论：**no-go**（针对框架当前的形态）

按定稿阈值 15% 推算（Rust 侧开销取实测 51 µs）：

| Worker 体时长中位数 | 当前占比 | Rust 化后占比 | 判读 |
|---|---|---|---|
| 0.046 ms | 70.9% | 53.5% | 两者都远超阈值，**Rust 也救不了** |
| 0.31 ms | 25.9% | 15.2% | 恰在阈值边界 |
| 2.7 ms | 4.3% | ~1.7% | 两者都在阈值内，**不必要** |
| 10.3 ms | 2.1% | ~0.6% | 同上 |

**15% 阈值的交叉点**：当前框架开销约 113 µs，交叉点在 Worker 体约 **640 µs**；
Rust 化后（开销约 51 µs）交叉点降到约 **290 µs**。

也就是说，**Rust 化只在 Worker 体中位数落在 290–640 µs 这个窄带内时，才把结论从
"不必要"变成"有必要"**。而在这个窄带里，收益上限也只有 **1.67x**。

对照引入 Rust 的确定成本——maturin 构建链、6+ 平台 wheel 矩阵、CI 增加 Rust 工具链、
混合堆栈调试、Rust panic 风险、失去纯 Python 的"可读源码、可热改、pip 直接装"属性——
**收益不足以支撑，建议 no-go**。

### 这个结论的适用边界

上述对照测的是**框架当前的形态**：把一段 Python 执行体派发出去、执行、收回完成信号。
在这个形态下，瓶颈是 GIL 与跨线程唤醒，Rust 拿不走多少。

**若目标是一个真正的 Server 运行时**（Rust 全程处理连接与协议、Python 只在请求到达时
被调用一次），那是**另一种架构**：Rust 承担的是它自己能独立完成的工作，不经受本对照
中的 GIL 往返。该架构的收益**未被本次 PoC 测量**，需要单独的 PoC——它测的应该是
"Rust 处理 N 个并发连接的吞吐"，而不是"派发 Python 回调的延迟"。

## 四、在考虑 Rust 之前：还有两处未兑现的纯 Python 收益

### 1. `concurrent.futures` 的记账占了派发成本的绝大部分

```
ThreadPoolExecutor.submit().result()  : 31.9 µs   ← 当前实现
queue.Queue.put + 工作线程消费（无 Future） : 1.86 µs   ← 纯 Python 的下限
```

换掉它是纯 Python 改动，成本远低于引入 Rust，而它触及的正是框架开销里占比最大的一段。

### 2. 四项"阻塞 Rust 化的优化"至今未落地

design 的 P1 把它们列为 `fix-worker-scheduling` 的一部分，但**该变更的 tasks 从未包含
它们**——属任务表编写疏漏（见「未完成项」）。

| 优化项 | 实测差距 |
|---|---|
| 事件管道去 `gevent` | 38.1 µs vs 47.5 ns（**800x**） |
| `ThreadSafeDict` 换 `threading.RLock` | 2056 ns vs 155 ns（**13x**） |
| `BaseFIFO` 换 `deque` | 队列 10k 时 12.4x |
| 默认启用资源池 | 线程模式 222 µs vs 池模式 13.5 µs（**16x**） |

**建议**：先做这两项纯 Python 优化并重测。它们的量级远大于本次测得的 Rust 收益，
而且不需要新的构建链与发布矩阵。

## 五、需要你确定的一件事

**本项目要做的是 Worker 编排框架、Server 框架，还是两者兼具？**

结论已经不依赖"Worker 体的具体粒度"了——**在框架当前的形态下，任何粒度都不值得上
Rust**（细粒度档 Rust 也救不了：占比 53.5% 仍远超阈值；粗粒度档本来就不需要）。
真正剩下的问题是架构方向：

- **继续做 Worker 编排框架** → **no-go 定案**。转去做第四节的两项纯 Python 优化，
  它们的实测量级（12x–800x）远大于 Rust 能带来的 1.67x
- **转做 Server 运行时** → 需要**另一个 PoC**。它的对照不该是"派发 Python 回调的延迟"
  （本次已证明这条路上 GIL 是瓶颈），而应该是"Rust 处理 N 个并发连接的吞吐 vs
  Python asyncio/granian"。那是完全不同的一层，Rust 在那里才可能拿到数量级收益
- **两条线都要** → 同"继续做 Worker 编排框架"，Rust 只对 Server 侧有意义

| macOS 抽样验证 | **未完成** | 本机无 macOS 环境，需要 CI 的 `macos-latest` | 并入待立变更 `align-execution-primitives` 的复测任务 |

**三项与本次裁定相关的实测补充（2026-09-27 复核）：**

1. **`gevent` 只有两处使用**，且**不可拆分**：`workers/event_worker.py`（事件管道）与 `statemachine/state_node.py` 的 `_perform_effect`（状态写路径）。后者同时是**行为**问题——`set_value` 会在写路径上阻塞等待观察者，最长 5 秒（`gevent.joinall(timeout=5)`）。依赖 `gevent` 只有在两处都清掉后才能从 `pyproject.toml` 移除，故三项优化必须同属一个变更。
2. **`ThreadSafeDict` 仍是模块级单把 `multiprocessing.Lock`**，即全进程串行。换锁时不应只换类型，还应把"全局单锁"改为按实例或按作用域——这与 `scoped-container` 要求的线程安全归属声明是同一条线。
3. **「默认启用资源池」的风险已低于本表编写时的水平**：内核已获得 `WORKER_MODE` 参数（`worker:mode`，未实现的模式明确拒绝而非静默降级）与 `worker:pool:enabled` 的历史键名别名兼容，且线程模式与池模式现在**共用单一结算点**上报结果（`_on_worker_done`）。因此把默认值由 `False` 改为 `True` 不再是结果投递的行为变更，只剩资源边界与背压的变化。
