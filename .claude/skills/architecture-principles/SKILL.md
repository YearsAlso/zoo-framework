# Architecture Principles — 架构设计原则

设计代码架构时必须遵循的原则体系。**硬性约束不可违反**；**必备能力是每次架构设计必须执行的动作**；**输出规则是违规时必须的反馈形式**。

## 使用场景

- **software-engineer**：设计/编写代码架构时强制遵循（设计先行于编码）
- **reviewer**：architecture-review 审查时校验硬性约束，发现违规按输出规则告警
- **architecture-reasoning**：推演出的设计方案必须满足本 skill 的硬性约束

## 硬性约束（不可违反）

### 1. 整洁架构分层

- 依赖方向：**实体 → 用例 → 适配器 → 外部组件**，依赖仅允许外向内（内层禁止依赖外层）
- 核心逻辑（用例层）禁止直接依赖框架/存储/网络实现
- 跨层交互必须使用抽象（协议/ABC/接口），实现落在外围
- 本项目对应：`core/` 内核不依赖具体 Worker 业务实现；`utils/`、`constant/` 稳定层不反向依赖易变层
- 违反判断：内核/稳定层出现对上层或外部技术的直接引用 → 🔴 阻断

### 2. 适配器隔离

- 框架、第三方依赖必须用适配器隔离，业务代码不能绑定外部技术
- 外部依赖替换（换队列实现/换存储/换并发原语）只允许修改适配器层，不波及业务
- 违反判断：业务类直接使用第三方类型作为公开方法签名/属性（未经抽象隔离）→ 🔴 阻断

### 3. 重构纪律

- 重构不改动外部行为（公共 API、装饰器语义、持久化格式、事件契约不变）
- **无测试不做大重构**；小步迭代，每步可运行、可测试
- 重构与新功能代码**分开提交**，禁止混在一次提交中
- 违反判断：重构改变了对外契约或与功能代码同提交 → 🔴 阻断

### 4. 代码质量底线

- 杜绝：重复代码（DRY）、巨类（>400 行）/长函数（>60 行）、魔法数字、模糊命名
- 新增代码必须达到：命名自解释、单一职责、复杂度可读
- 违反判断：明显重复实现/超长方法/裸数字/含义不明命名 → 🟡 警告（巨类长函数可升 🔴）

### 5. 渐进改造

- 优先渐进改造，不轻易全盘重写（重写 = 高风险，必须走 architecture-reasoning 推演 + 明确理由）
- 临时妥协（如硬编码、跳过重构、保留旧全局状态）必须标记技术债务：位置 + 原因 + 偿还时机
- 违反判断：大范围重写无推演记录 / 临时妥协无技术债标记 → 🔴 阻断

### 6. 开闭原则

- 稳定模块不依赖易变模块；对扩展开放、对修改封闭
- 新增需求优先走"扩展"（新 Worker/新 SchedulerModel/新 StateIndex 实现），不走"修改稳定代码"
- 本项目已有清晰扩展缝：`SchedulerModel`（ThreadPerTask/ThreadPool）、`StateIndexFactory`、`PersistenceStrategy`、`Plugin` — 优先在其上扩展
- 违反判断：为新增需求修改已稳定模块核心逻辑（可扩展而未扩展）→ 🟡 警告（影响大升 🔴）

## 必备能力（每次架构设计必须执行）

| 能力 | 动作 | 执行时机 |
|------|------|---------|
| 非法依赖自动校验 | 检查新增 import 的方向（内核是否依赖上层、稳定层是否反向依赖、跨层直引） | 编码前设计完成时 |
| 分层越界检测 | 检查各包职责是否越界（core 写业务逻辑、worker 直操作外部存储） | 编码前设计完成时 |
| 坏味道识别与重构方案 | 识别重复/巨类长函数/魔法数字/模糊命名/过度耦合，给出可落地重构方案 | 设计评审与审查时 |
| 防腐适配器设计 | 对外部依赖（第三方库/gevent/pickle/未来的 Rust 核心）主动设计防腐层，业务侧只见抽象 | 引入新依赖时 |
| 依赖风险评估 | 改动前评估：变更影响面、被依赖方稳定性、替换成本、升级风险 | 任何架构/依赖变更前 |
| 业务与实现隔离 | 用例逻辑不感知存储/线程/网络细节，全部经抽象委托 | 编码前设计完成时 |

## 输出规则

- 发现违规架构、代码问题时**主动告警**，不得沉默通过
- 告警格式：`文件:行号` + 违反的约束编号（如"约束 2 适配器隔离"）+ 严重级别 + **可落地的修改方案**（具体到改哪个文件/加哪个抽象/如何调整依赖）
- 严重级别沿用统一分级：🔴 阻断（必须修复）/ 🟡 警告（建议修复）/ 🔵 建议（可选）

## 与相关 skill 的关系

- **architecture-review**：按本 skill 的硬性约束作为审查维度执行
- **architecture-reasoning**：推演设计时以本 skill 为约束底线；冲突时优先本 skill
- **architect-memory**：本 skill 红线被违反并修复后，由 reviewer 转交 architect 记录教训到架构记忆
