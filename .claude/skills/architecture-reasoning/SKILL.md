# Architecture Reasoning — 架构推演思考

在架构/设计决策前进行前瞻性推演，把"这个改动未来会怎样"想清楚再动手，并把推演记录下来供后续验证与校准。

## 核心目标

1. **长期影响推演**：本次改动对架构（分层、依赖、可扩展性、可维护性、兼容路径）的长期影响是什么？是否引入技术债？一年后的视角是否仍合理？
2. **短期变更可能性推演**：基于需求脉络，未来短期内（1-3 个迭代）可能出现哪些需求变化？本次设计是否为此留了扩展点？
3. **复盘校准**：新需求到来时，先翻看既往推演记录，用实际结果校验推演是否准确，持续纠正自己的推演能力。

## 触发时机

- 新需求进入 SDD（OpenSpec）的 Proposal/Design 阶段（架构形态未定时）
- 架构/依赖/`@cage` 单例注册/技术选型发生变更（与 architecture-review 配合：先推演、后审查）
- 出现"临时妥协"（标记技术债时必须附带长期影响推演）
- 新需求评审时（必做：翻看推演记录 → 复盘）

## 推演流程

### Step 0: 翻看推演记录（每次新需求必做）

推演记录已拆为活跃 + 归档两个文件（降低单文件体积）：
- `docs/memory/architect-reasoning.md`：活跃推演（近期 R-记录 + 复盘校准日志）
- `docs/memory/architect-reasoning-archive.md`：历史推演（迁移过来的旧记录）

新需求到来时，**用 Grep 定位相关既往推演，禁止全文读取**：先 `Grep '### R-' docs/memory/architect-reasoning.md` 取标题行号，按关键词命中区间用 Read 精读；需回溯更早历史时再查 `architect-reasoning-archive.md`。然后按以下顺序梳理：

1. 找出与本需求相关的既往推演记录（按关联模块/需求匹配）
2. 逐条核对推演中的"预测"是否被本需求验证：
   - 预测的需求变化真的出现了？→ 设计预留是否命中？
   - 预测的变化没出现？→ 该条推演方向偏了
   - 出现但预测偏差大？→ 记录偏差原因
3. 将复盘结果写入该记录的"复盘"小节（见下），并更新"复盘校准日志"
4. **带着复盘结论进入本需求的设计**：吸取历史教训，避免重复同样的推演错误

### Step 1: 关联需求上下文

- 用 Grep 定位 `docs/memory/pm-memory.md` 中需求上下文的行区间后精读（需求主线、关键约束），禁止全文读取
- 浏览 `openspec/specs/` 与 `openspec/changes/archive/`：同能力/相邻能力的 spec 演化脉络（哪些需求是连续的、哪些是修补性的）
- 确定本次需求在需求脉络中的位置

### Step 2: 长期架构影响推演

回答以下问题，逐项给出结论：

| 推演项 | 问题 | 结论 |
|--------|------|------|
| 分层影响 | 改动是否触及分层边界？`core/` 是否引入新依赖？ | {结论} |
| 依赖方向 | 是否新增跨层/逆向依赖？是否违反整洁架构（实体→用例→适配器→外部组件）？ | {结论} |
| 扩展性 | 新增同类需求时，本次设计是"自然扩展"（走 SchedulerModel/StateIndex/Plugin 缝）还是"需要重构"？ | {结论} |
| 技术债 | 是否引入临时妥协？预期偿还时机与成本？ | {结论} |
| 兼容/跨平台路径 | 是否影响持久化存档兼容、跨平台（Win/Linux/macOS）行为、公共 API 契约？ | {结论} |
| 可维护性 | 是否新增巨类/重复/魔法数字/模糊命名？是否违反开闭原则？ | {结论} |

### Step 3: 短期需求变更可能性推演

基于需求脉络推演：**未来 1-3 个迭代内，与本模块相关的最可能出现的 2-5 个需求变化**。

| 可能性 | 需求变化 | 依据（来自既有需求脉络） | 本次设计应对 | 若未应对的代价 |
|--------|---------|--------------------------|--------------|----------------|
| 高/中/低 | {变化} | {依据} | {留了扩展点 / 未留} | {代价} |

推演原则：
- 只推演**有依据**的变化（来自 openspec 历史、需求主线、ROADMAP/OPTIMIZATION_PLAN 趋势），禁止凭空脑补
- 依据不足的列为"低可能"，标注依据来源
- 高/中可能的需求变化，设计上必须给出应对（扩展点或明确拒绝的理由）

### Step 4: 输出推演记录

将推演结果按"推演记录结构"追加到 `docs/memory/architect-reasoning.md`（活跃文件）。**未记录 = 未推演**，推演必须留痕。当活跃文件 R-记录超过 8 条时，把最旧的记录迁移到 `architect-reasoning-archive.md`（保持活跃区精简）。

## 推演记录结构（docs/memory/architect-reasoning.md）

每条记录格式：

```markdown
### R-{序号}：{关联需求/变更名称}（{日期}）

- **关联**：{openspec/specs/<capability> 或 change id} | **模块**：{模块名}
- **状态**：进行中 / 已复盘 / 已失效

**长期影响推演**：
- 分层/依赖：{结论}
- 扩展性：{结论}
- 技术债：{结论}
- 兼容/跨平台：{结论}

**短期变更可能性推演**：
- 高可能：{变化 1} → 应对：{扩展点或拒绝理由}
- 中可能：{变化 2} → 应对：{...}
- 低可能：{变化 3} → 应对：{...}

**预期验证点**：{哪些信号出现时说明推演正确/错误}

---

#### 复盘（R-{序号}）
- **验证日期**：{YYYY-MM-DD} | **验证需求**：{触发复盘的新需求}
- **预测命中**：{哪些预测被验证/命中}
- **预测偏差**：{哪些预测落空或偏差，偏差原因}
- **经验修正**：{下次推演要调整的思维模式/方法}
```

## 复盘校准日志（docs/memory/architect-reasoning.md 末尾）

每次复盘后，在"复盘校准日志"追加一行，沉淀推演能力的纠偏：

```markdown
| 日期 | 推演编号 | 偏差类型 | 修正要点 |
|------|---------|---------|---------|
| {日期} | R-{n} | 过度设计/设计不足/方向遗漏/命中 | {下次如何调整} |
```

**偏差类型定义**：
- **过度设计**：推演了未出现的需求变化，设计过度预留（记：如何判断依据强度）
- **设计不足**：推演到了但未留扩展点，或未推演到的变化出现了（记：哪些信号该更早关注）
- **方向遗漏**：出现的变化方向完全在推演范围之外（记：需求脉络中哪些线索被忽略）
- **命中**：推演准确（记：哪些判断依据有效，可复用）

## 推演纪律

- **先看记录、后做设计**：任何新需求设计前必须翻看推演记录（Step 0），遗漏复盘即流程违规
- **推演必须有依据**：每个"可能性"都要写出来源（openspec 历史/需求主线/ROADMAP 趋势），禁止凭空脑补
- **记录必须留痕**：推演结论写入 architect-reasoning.md，禁止口头推演
- **与 architecture-review 的分工**：本 skill 管"未来会不会有问题"（前瞻推演），architecture-review 管"当前有没有问题"（现状审查）；先推演后审查
- **与 architecture-principles 的关系**：推演出的设计必须满足 architecture-principles 的硬性约束；发现原则冲突时优先原则
