# 通俗总结规则 — Plain Summary

## 原则

**每次有实质性产出的回答，必须在末尾附一段「通俗总结」**，标准为：一个不懂技术的人读完也能知道「做了什么、结果如何、下一步是什么」。

总结的目的是省读，不是重复正文——必须是提炼。

## 要求

| 项 | 标准 |
|----|------|
| 篇幅 | 3 句话以内（约 100 字） |
| 结构 | 做了什么 → 结果 / 影响 → 下一步（如有） |
| 术语 | 技术名词必须转成日常语言或打比方 |
| 位置 | 回答末尾，以「通俗总结」作为标题 |

术语转换示例：

- 「插件」→「可直接安装使用的功能包」
- 「hooks 门禁」→「提交前自动检查的关卡」
- 「性能探针脚本（bench/）」→「专门用来测速的小程序，帮我们判断优化值不值得做」
- 「状态机存档（pickle）」→「把程序当前状态拍照存到文件，重启后能接着用」

## 禁止行为

- ❌ 总结中堆砌技术术语（禁止直接罗列英文名词 / API 名 / 类名）
- ❌ 总结中出现代码、日志、长文件路径
- ❌ 复述正文全部内容（总结与正文等长即失败）
- ❌ 总结引入正文未提及的新信息

## 例外

以下场景可不附通俗总结：

- 用户明确要求详细技术说明（按用户要求输出）
- 纯提问 / 确认类回答（无实质产出）
- 回答正文本身已足够通俗简短（不超过 3 句）
