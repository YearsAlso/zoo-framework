# Workflow: bugfix — Bug 修复

本文件是该 workflow 的唯一规范源。路由规则与场景信号见 `.claude/agents/leader.md`，主对话按本文件编排阶段序列执行。

## 适用场景

报错 / bug / 崩溃 / 异常 / 不生效 / 修复 / 改一下（弱信号：逻辑问题 / 行为不符 / 验证）。行为修复（改行为使结果正确）。

## 阶段序列

| 阶段 | 负责人 agent | 输入 | 产物 |
|------|-------------|------|------|
| 1. 场景确认 | pm | 用户请求 + 复现信息 | bug 影响范围 + 契约边界 |
| 2. 定位 | code-indexer | bug 描述 | 根因分析（全链路）+ 影响面预判（需求归属/架构影响/风险等级） |
| 2.5 同类排查 | bug-investigation-memory | 根因分析 | 排查记忆文档（docs/memory/bug-investigation-memory.md） |
| 2.7 修复策略决策 | pm | 根因分析 + 影响面预判 + 同类排查结果 | 修复策略决策（最小修复/彻底修复/切换 workflow） |
| 3. 最小修复 | software-engineer | 修复策略 + 根因 | 代码修改（<20 行免 SDD） |
| 4. 回归测试 | unit-tester | 修复代码 | 针对性用例 + ruff + 单目标 pytest ≤10s |
| 5. 轻量审查 | reviewer | 修复代码 | security 必查；🔴 则 audit-report 落盘 |

## 裁剪规则

- 最小修复 <20 行免 SDD（sdd.md）；轻量审查不等同免审查，security 维度必查
- 影响面预判为"无架构影响 + 同级修改" → 修复策略决策阶段可跳过，默认"最小修复"
- 用户明确"只修这里，不查同类" → 跳过阶段 2.5 同类排查
- 简单 bug（如 typo、单行逻辑错误、配置值错误）→ 跳过阶段 2.5 同类排查 + 2.7 决策，直接修复

## 影响面预判（阶段 2 产物）

code-indexer 定位阶段除根因分析外，需输出以下影响面预判供阶段 2.7 决策：

### 需求归属判定
| 分类 | 判定标准 | 示例 |
|------|---------|------|
| 代码 bug | 有明确规格，实现与需求不符 | 空引用、条件判断错误、调用链缺失 |
| 需求缺失 | 规格未定义该场景，当前行为符合代码逻辑但不符合预期 | 未处理边界输入、缺少错误提示 |
| 配置错误 | 行为符合代码逻辑，但配置值不正确 | 超时值过小、路径配置错误 |

### 架构影响预判
| 等级 | 判定标准 | 示例 |
|------|---------|------|
| 无影响 | 同级修改，不跨越分层 | 方法内逻辑修正、表达式修改 |
| 局部影响 | 跨层但不改变契约 | 同一层内新增方法、内部逻辑调整 |
| 跨层影响 | 涉及装饰器注册、公共 API 签名、持久化格式、新增依赖 | 新增导出符号、修改装饰器语义、改存档结构 |

### 风险等级
| 等级 | 判定标准 |
|------|---------|
| 🟢 低 | 影响范围明确（≤2 文件），无架构影响，无契约影响 |
| 🟡 中 | 影响范围 ≤5 文件，或涉及局部架构影响，或涉及核心不变量 |
| 🔴 高 | 影响范围 >5 文件，或跨层影响，或涉及持久化格式/公共 API 变更 |

## 修复策略决策门禁（阶段 2.7）

| 决策条件 | 路由 | 说明 |
|---------|------|------|
| 根因为需求缺失（需求未定义、规格不明确） | 切换 feature-dev | 原 bug 作为需求上下文移交 pm-memory |
| 修复方案涉及跨层依赖/装饰器注册变更/公共 API 签名变化 | 切换 feature-dev（architect 介入） | 行为修复 + 架构变更，不再是最小修复 |
| 修复方案影响持久化格式（存档结构/备份策略） | 切换 feature-dev（architect + persistence-review） | 存档变更走完整 SDD 流程 |
| 根因为配置错误/环境问题 | 直接修复（不切换） | 同步更新配置文档 |
| 根因为代码 bug，无架构影响 | 继续 bugfix（最小修复） | 默认路径 |
| 修复范围扩大为新增功能/重构 | 中止并切换 feature-dev（输出切换记录） | 边界升级条件，通过决策门禁显式捕获 |

## 审查与验证的串行纪律

**审查（只读）与验证（会改写被测对象）不得并发。**

### 由来
一次变更中，只读审查（reviewer）与「**临时注入违规实现以验证断言是否有牙齿**」的验证（unit-tester）被并发派发 ⇒ 审查方读到**注入态**，把**验证探针误报为 P0 缺陷**并写入审计报告 —— 交付物出现假记录。

### 纪律
| 序 | 规则 |
|---|---|
| 1 | **串行**：标准序 = **冻结 → 审查 → 解冻 → 注入验证**。绝不让"只读审查"与"会改写被测文件"的验证并发 |
| 2 | **注入标记**：注入的代码须带**醒目且可机检**的标记（如 `# VIOLATION-` / `# TRANSIENT-PROBE`），使第三方可辨识 |
| 3 | **哈希锚定**：审查结论**必须绑定被审文件的 md5**，并写明"本结论仅对该哈希有效"；落盘前**核对被审文件哈希在审查窗口内是否变过，变过则结论作废重跑** |
| 4 | **探针优先**：收到"并发期间发现 P0"的报告时，**先查是否存在注入探针，再判定为缺陷** |
| 5 | **留痕**：注入与还原过程须留痕（记录 md5 / 备份），作为验证报告附件，使断言有效性可被第三方复核 |

### 与并发构建污染同族
并发写同一模块/共享缓存会互相污染（伪造"缺成员/被截断"的错误）；并发"审查 + 注入验证"会**伪造 P0 缺陷**。二者同属"**并行 agent 互相污染**"，处置同理：**先假设污染/探针，串行复核后再判定为缺陷**。

> 断言有效性的判定标准见 `.claude/rules/assertion-integrity.md`。
