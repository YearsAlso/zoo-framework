# Workflow: technical-research — 技术调研

本文件是该 workflow 的唯一规范源。路由规则与场景信号见 `.claude/agents/leader.md`，主对话按本文件编排阶段序列执行。

## 适用场景

调研 / 研究 / 探索 / 了解 / 学习 / 调查（弱信号：查一下 / 看看 / 了解一下）。技术可行性调研、新技术评估、知识收集。不涉及代码实现或架构决策落地。

## 阶段序列

| 阶段 | 负责人 agent | 输入 | 产物 |
|------|-------------|------|------|
| 1. 范围确认 | pm | 用户请求 | 调研问题清单 + 边界限定（研究范围 / 不研究范围） |
| 2. 调研执行 | architect | 调研问题 | 调研报告（技术原理/方案对比/适用性分析/与项目结合点）+ 必要时多源检索（WebSearch/WebFetch）交叉验证 |
| 3. 决策记录 | architect | 调研报告 | 结论与建议（ADR 追加至 architect-decisions.md，若涉及架构影响） |
| 4. 归档 | pm | 调研报告 | pm-memory 需求上下文记录 |

## 裁剪规则

- 纯信息获取（无后续实施可能）→ 跳过阶段 3-4，直接输出调研报告
- 调研结论建议进入实施 → 另起 feature-dev 或 design-doc（调研资产复用）
- 快速查询（< 5 分钟可答）→ 跳过阶段 1-2，直接回答

## 边界与升级

- 调研结论若涉及架构选型 → architect 按 architecture-reasoning 完成推演后决策
- 调研同时需要代码原型验证 → 调研阶段产出原型方案，另起 feature-dev 正式实现
- 涉及性能可行性的调研（如 Rust/并发原语）→ 数据须来自 bench 实测或权威基准，必要时先由 perf-guardian 补测，禁止臆测数字
- 与 design-eval 的边界：technical-research 是"先了解再决策"，design-eval 是"给定多个方案选最优"；调研先行，评估后续
