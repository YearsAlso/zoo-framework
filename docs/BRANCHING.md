# 分支模型与访客可见性 (Branching)

> 本文定义 `main` / `dev` 双分支的职责分工，以及一类特殊的承诺：**访客可见面**（visitor-visible
> surface）。分支操作规范（怎么切分支、PR 指向哪）见 [CONTRIBUTING.md](../CONTRIBUTING.md)
> 的「分支规范」一节，本文不重复。

## 双分支职责

| 分支 | 职责 |
|---|---|
| `main` | 发版分支，也是 GitHub **默认分支**——GitHub 网页、搜索引擎、外部链接的默认入口。只在发版时接收来自 `dev` 的合并。 |
| `dev` | 集成分支。所有功能/修复 PR 都合并到这里；push 到 `dev` 发布 `-beta` 版本。 |

## 访客可见面

以下文件因为默认分支的关系会被外部读者直接看到，它们的定义与维护规则是本承诺的核心：

| 文件 | 可见性要求 |
|---|---|
| `README.md` / `README.zh.md` | 项目定位、能力表、Quick Start。正文主体随发版下发（见下节）。 |
| `SECURITY.md` | 安全报送渠道与支持版本策略。**以 `dev` 为唯一编写点**，main 只接收同步。 |
| `LICENSE` | 许可证文本。 |
| `CODE_OF_CONDUCT.md` | 行为准则。 |
| `CONTRIBUTING.md` | 贡献入口指引。 |

## 可见性承诺

**规则 1 — 事实性修复同一发布周期内可见于 main**
当上述访客可见面文件在 `dev` 上完成**事实性修复**（版本声明、错误描述、支持策略、
失效链接等，且不依赖 dev 独有/未发布的功能）时，该修复必须在同一发布周期内同步到
`main`。不存在"dev 上修好了但 main 一直显示错的"的中间态。

**规则 2 — 功能类内容随发版下发**
依赖未发布功能的改动（例如 README 新特性的叙述、新文档章节）**不属于**违反可见性
承诺——它们随下次发版自然进入 `main`。把这类差异误判为"漏改"会引发不必要的手工搬运，
请按下节的检查方法区分两类差异。

**规则 3 — 治理文件单一编写点**
`SECURITY.md` 等治理文件以 `dev` 为唯一编写点：修改一律先落在 `dev`，再按规则 1 同步
到 `main`。MUST NOT 只在 `main` 上修改治理文件——那会制造 main/dev 内容分叉，进而让
下次发版合并时产生冲突或静默回退。

## 漂移检查

把下面这条命令粘贴到任意 clone 里执行，即可审计访客可见面的 main/dev 差异：

```bash
git diff origin/main...origin/dev -- README.md README.zh.md SECURITY.md LICENSE CODE_OF_CONDUCT.md CONTRIBUTING.md
```

判读：

- 差异属于**事实性修复**（版本号、错误描述、支持策略、失效链接）→ 违反规则 1，需要同步到 main。
- 差异属于**随发版内容**（dev 上未发布的新特性叙述、重写正文）→ 正常，规则 2 豁免。
- `SECURITY.md` 出现任何差异 → 一律违反规则 3（该文件在 main 上不应有 dev 之外的演化）。

## 历史

- 本承诺由 `branch-doc-sync` change 建立；建立时 main 上的 `SECURITY.md` 仍声明
  `0.5.3-beta`（项目实际已是 0.10.x），作为违反规则 1 的实例被回并修复。
- `main..dev` 的提交数在同一个 change 的 propose 与 apply 阶段从 29 增长到 52——
  漂移不会自动消失，只会变大。发现即修，依赖本页的检查命令而非记忆。
