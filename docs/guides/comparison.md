# 与其它方案对比

> **口径**：本页比较各项目的**公开定位与能力面**，**未做跨项目基准测试**。
> 我们在这里明确写出"什么时候不该用本框架"。

## 总览

| | Zoo Framework | Celery | APScheduler | 裸 `threading` |
|---|---|---|---|---|
| 部署形态 | 嵌入你的进程 | 独立 worker + broker | 嵌入 | 嵌入 |
| 外部依赖 | **无** | Redis / RabbitMQ | 无 | 无 |
| 跨机器 | ❌ | ✅ | ❌ | ❌ |
| 多进程 | ❌ 未实现 | ✅ | ❌ | ❌ |
| cron 表达式 | ❌ | ✅ beat | ✅ | ❌ |
| Worker 生命周期 | ✅ | 部分 | ❌ | 自己写 |
| 在飞去重 | ✅ | ✅ | 部分 | 自己写 |
| 超时处理 | ✅ 观察 + 熔断 | ✅ | ❌ | 自己写 |
| 事件管道 / 优先级 / 重试 | ✅ | 部分（队列） | ❌ | 自己写 |
| 内建状态持久化 | ✅ 原子替换 + 滚动备份 | 依赖 result backend | 依赖 job store | ❌ |
| 失败方式 | 大声报错 | 多数明确 | 多数明确 | **通常静默** |

## 什么时候该用 Celery

- 任务需要**跨机器**执行
- 需要**多进程**（CPU 密集且想要真并行）
- 需要**任务队列的持久化**：进程崩溃后未完成的任务还在
- 需要成熟的**监控与运维生态**（Flower 等）
- 团队已经在用，不想再加一套

**在以上任何一条成立时，Celery 是正确答案，本框架不是。**

## 什么时候该用 APScheduler

- 需要 **cron 表达式**
- 只需要"按时间调用一个函数"，不需要任务生命周期
- 需要比本框架更长的**稳定历史**

**本框架在 cron 上不如 APScheduler，这一点不加修饰。**

## 什么时候该用裸 `threading`

- 只有一两个任务，且永远不会有第三个
- 你完全清楚在飞管理、停机顺序与异常处理该怎么做

**但请注意**：裸 `threading` 的典型失败方式是**静默**——任务停了没人知道，
或者两个实例意外并发跑起来。本框架存在的理由就是把这些失败变成会响的。

## 什么时候该用本框架

同时满足这几条时，它是最省事的选择：

1. 任务**就该待在你的进程里**（不是"没想过要不要拆出去"）
2. **不值得为此引入 broker** 或运维一套 worker 集群
3. 你需要**生命周期、在飞去重、超时熔断中的至少一项**
4. 你希望**重启后状态能恢复**
5. 你能接受"跨机器/多进程/cron 都做不到"

第 5 条不是免责声明，而是**范围声明**：本框架刻意做窄，把上述三条让给更合适的工具。

## 和 asyncio 的关系

| | 本框架 | 纯 asyncio |
|---|---|---|
| 并发模型 | 线程 | 单线程事件循环 |
| CPU 密集任务 | 可以（线程池） | 会阻塞整个循环 |
| 阻塞式同步库 | 可以直接用 | 需要 `run_in_executor` 包装 |
| 协程支持 | 通过 `AsyncWorker` | 原生 |

框架也提供 `AsyncWorker`，用于需要协程的任务；但它**不是**把整个调度器变成 asyncio。

## 与 orchestration 平台的区别

Dagster / Prefect / Airflow 这类是**数据管道编排平台**：它们的中心是"任务图 + 调度 + 观测面板"，
通常需要独立的调度器进程与数据库。

本框架的中心不是"图"，而是**一个进程内长期存活的执行环境**。
需要可视化面板、依赖图、跨团队共享调度时，用那些平台。
